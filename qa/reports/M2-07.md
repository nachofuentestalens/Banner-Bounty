## Defect found: malformed JSON body returns `500 internal`, not `400 validation` (P2)

**Where:** `apps/server/src/app.ts`, `setErrorHandler` (around line 79). The handler has explicit
cases for `AppError`, `ZodError`, and Fastify's `FST_ERR_CTP_BODY_TOO_LARGE`/413 (all correctly
mapped to `400 validation`), but no case for Fastify's JSON-parse failure
`FST_ERR_CTP_INVALID_JSON_BODY` (which Fastify itself reports as `statusCode: 400`). That error
falls through to the generic branch and is reported as `500 internal`.

**Reproduction (deterministic, reproduced on 2 separate runs):**

```
POST /expedition/settle
Content-Type: application/json
Cookie: <valid session cookie for an existing account>
Body: {not valid json

-> HTTP 500
-> { "ok": false, "error": { "code": "internal", "message": "internal error", "correlationId": "..." } }
```

Server console simultaneously logs this as a real internal error:
`[server] internal error (correlationId=...) FastifyError [Error]: Body is not valid JSON but
content-type is set to 'application/json' ... code: 'FST_ERR_CTP_INVALID_JSON_BODY', statusCode: 400`.

**Why this matters:** `design/studio/contracts.md`'s "Conventions" section states "Bounded inputs:
... Zod schemas enforce this at the HTTP boundary; violations return `validation`." A malformed
JSON body is exactly this class of client-input violation — Fastify itself already classifies it
as a 400-level error — but the app's own handler re-labels it `internal`/500. Two consequences:
(a) a client cannot distinguish "I sent something invalid" from "the server broke," which is the
specific ambiguity `ErrorCode`'s `validation` vs `internal` split exists to avoid; (b) every
malformed-JSON request from a real client (e.g. a buggy future client build, a proxy that mangles
a body, or a user replaying a corrupted browser-storage draft) will show up in server logs and
monitoring as a genuine internal error, polluting error-rate signals that are meant to indicate
real server faults.

**Severity: P2.** Not a crash, not data loss, not reachable by normal UI use (the shipped client
always sends well-formed JSON), and the server stays healthy and keeps serving correctly afterward
(confirmed: `tests/e2e/malformed-payloads.mjs`'s final health check passes every run). It is a
genuine, reproducible contract-conformance gap, not a release blocker.

**Suggested fix shape (not applied by this task — out of QA's write scope):** add a case to
`setErrorHandler` for `fastifyError.code === "FST_ERR_CTP_INVALID_JSON_BODY"` (or more generally,
any Fastify `FST_ERR_CTP_*` content-type-parser error, which are all genuinely client-input
problems) alongside the existing `FST_ERR_CTP_BODY_TOO_LARGE` case, mapping it to
`400 validation` the same way.
