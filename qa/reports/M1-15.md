### Defects found and fixed during this task (all in QA's own test code, not the product)

1. `api-attacks.mjs` A05.1/A05.2 initially looked up `inventory[i].slot`, which does not exist — `ItemInstance`
   rows only carry `definitionId`; slot is a property of the item *definition* in `packages/content`, not the
   instance. Fixed by deriving slot from the `item_<slot>_...` ID prefix. Before the fix this produced a
   false "no weapon in inventory" / spurious `404` rather than a false pass, so no incorrect pass was ever
   reported.
2. `boss-arena.mjs` A09.1/A09.3 compared `report.result !== "win"`, but `BattleReport.result` is an object
   (`{ outcome, rounds, finalHp }`); the comparison always failed regardless of the real outcome, masking the
   actual win/loss. Fixed to check `report.result.outcome`. This also resolved an apparent "first boss
   attempt lost" result, which was the bug, not a real loss — rerun after the fix showed a win with reward
   granted, matching M1-14's "level 3 is boss-ready" record.
3. `browser-ui.mjs` A11.1 used `assert.notMatch` (not a Node `assert` method) instead of
   `assert.doesNotMatch`, which threw before the UI action under test ran, cascading false failures into
   A11.3/A11.4 (they inherited a server state where the expedition had never actually started). Fixed the
   method name; all three then passed cleanly end to end.

Each fix is a one-line correction verifiable in `tests/e2e/*.mjs`; none touched product code.

## Unresolved issues / limitations

1. **Boss-loss recovery not independently exercised.** Every boss attempt in this task's runs won (heroes
   reach level 3, which tuning.md documents as boss-ready). I did not force a loss to verify the UI's loss/
   retry path. M1-14 and M1-10 are recorded as covering this via earlier-level live losses; I did not re-run
   that here. This is a coverage gap for A09's "recoverable" clause, not a defect.
2. **Inventory-overflow boundary (100-item cap) not tested.** Acceptance.md's fixture list calls for
   "maximum inventory overflow"; this task did not run enough cycles to accrue 100+ unequipped items and
   verify the documented gold-conversion behavior. Flagging as untested, not passed.
3. **"Invalid request payload" and bounded-input limits not directly tested.** I exercised ownership, retry,
   concurrency, and precondition-order errors, but not a malformed/over-length body against the Zod schemas
   at the HTTP boundary.
4. **Only one simultaneous-*different*-command race was run** (two concurrent `settle` calls, A07.3). I did
   not test two different mutation types racing each other concurrently (e.g., an equip and a party-order
   change at once).
5. **Only Windows 11 with Playwright's bundled Chromium was tested**, not Edge (used by M1-14's walkthrough)
   or macOS/Linux. `tests/e2e` browser scripts default to Chromium rather than `msedge` for a fully
   self-contained install; this is a different browser engine than M1-14's manual walkthrough, which is a
   useful cross-check but not a substitute for Edge-specific verification.
6. **No contrast-ratio measurement or screen-reader test.** Same limitation M1-14 recorded; still open.
7. **Windows process signaling:** `restart-unaccelerated.mjs` found that `child.kill("SIGTERM")` from a
   parent Node process cannot deliver a real signal to a Windows child process (Node's own documented
   platform limitation — Windows "does not support sending signals"; the child is unconditionally
   terminated instead), so the server's own graceful-shutdown handler never ran in that automated check. The
   check was adjusted to assert what it *can* prove (port freed; data intact after an **abrupt** kill, which
   is a stronger claim than a graceful one) and documents the gap rather than asserting a graceful exit code
   that cannot be produced this way on Windows. M1-14 already verified the real human Ctrl+C / `Stop-Process`
   path manually ("nothing left listening").
8. **A03's full 3-class/3-specialization matrix was not independently re-walked this run**; this task's
   browser script stopped at the empty-state inspection of one spec picker (2 options) rather than selecting
   specializations for all three heroes. A03's pass verdict above combines this direct spot-check with
   M1-14's already-recorded fuller walkthrough evidence (Marksman/Guardian/Pyromancer); it is not a fresh
   independent confirmation of all three classes.

None of the above are P0/P1: no defect was observed in any of them, they are simply checks this task did not
reach. The release recommendation below treats them as open follow-up, not blockers.
