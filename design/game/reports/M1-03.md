## Acceptance checks

**1. Every M1 content ID has a concise display name and useful description; no copied Idle Adventure text.**
- Check: cross-referenced every ID in `content.md` sections 1-4 against `copy.md`: 3 classes, 6 specializations, 3 starter heroes, 9 item definitions, 3 affixes, 3 enemies, 1 boss — all present with a `.name` key, and the compound/stateful ones (classes, specs, area, boss, boss reward state) also carry a `.desc`.
- Check: all copy was written fresh for this task, describing only mechanics already frozen in `combat.md`/`content.md` (e.g., Guardian/Berserker/Marksman/Pathfinder/Pyromancer/Warden descriptions restate their existing frozen behavior in plain language, not new abilities). No text was taken from or paraphrased against the Idle Adventure store page; `vision.md` names it as a genre reference only, and this task did not open that page.
- Result: **pass**.

**2. Include local-build explanation, first expedition guidance, offline cap, loadout lock, inventory overflow, boss reward and arena snapshot explanations.**
- Check: `copy.md` section 5 contains `onboarding.local_build`, `onboarding.first_expedition`, `expedition.offline_cap`, `expedition.loadout_locked`, `inventory.overflow`, `boss.reward.pending`/`boss.reward.already_claimed`, and `arena.snapshot`/`arena.no_opponent` — matching `interface.md`'s "Required states" list (offline/reconnecting, expedition locking loadout, full inventory conversion, already-collected reward, no published opponent) and screen descriptions (local account selector explains local build; expedition screen needs first-run guidance; arena screen needs the "no fake live-player indicator" explanation).
- Result: **pass**.

**3. Specify lengths suitable for narrow UI (short labels, short descriptions) and avoid lore that introduces extra mechanics.**
- Check: `copy.md`'s header fixes three length bands (label ~24 chars, short description ~110 chars, body ~220 chars) consistent with `interface.md`'s 390px-wide stacked-panel requirement and "compact but readable stat tables." Item/enemy/affix rows use only label + short description; only onboarding/result copy uses the longer "body" band, and even those stay under ~220 characters (e.g., `onboarding.local_build.body` is 165 characters).
- Check: no description adds a mechanic beyond what's frozen — e.g., the Tollkeeper description names only the existing every-3rd-round targeting rule (`content.md` section 4), not a new attack; the Guardian/Berserker/Pyromancer/Warden lines restate `combat.md` 3.4/3.6 behavior without inventing a new stat or status.
- Result: **pass**.

**4. Provide implementation-ready keys and no dangling content references.**
- Check: every key follows a flat dotted convention (`<contentId>.name`, `<contentId>.desc`, or `<screen>.<state>.<field>`) directly usable as a lookup key in a future UI layer; the Implementation notes section states the affix-composition rule (`"{base name} {affix name}"`) so no new affix-display field is needed.
- Check: no key references an ID absent from `content.md` (verified by the full cross-reference in check 1) and no `content.md` ID lacks a key (same cross-reference, reverse direction).
- Result: **pass**.
