## Decisions and assumptions (recorded per `AGENTS.md` rule 4)

1. **`skillId` string scheme.** No file in the frozen surface (`classes.md`, `content.md`,
   `contracts.md`) fixes a concrete `skillId` string per skill — only a display name and a typed
   `string`/`string | null` field. I adopted `skill_<class>_<slug>` (e.g. `skill_vanguard_bulwark_call`)
   as a working, reversible convention so copy keys exist and implementers have something to bind to
   now, rather than blocking this task on a contract decision that is explicitly M2-25's to make. Noted
   in section 9: if M2-25 picks a different string scheme, only the key prefixes need renaming — the
   label/desc text is unaffected. This is the one place this task made a naming decision beyond pure
   copy; it is reversible and does not touch any frozen number or mechanic.
2. **No per-event feed-sentence keys.** Section 8.3 gives phrase fragments, not one key per every
   possible actor/skill/target/amount combination (which would be unbounded). Exact sentence assembly
   is left to M2-27 per M2.md's own division of labor (copy vs. UI implementation).
3. **No `status_*.desc` added.** Only `status_*.name` short labels are added for the 6 statuses. A
   `.desc` giving the exact magnitude/duration would either restate `classes.md` section 6's frozen
   numbers (risking drift) or require live numeric interpolation, which is M2-27's rendering concern,
   not new copy text — consistent with this document's "no lore implies an unfrozen mechanic" rule.
4. **No synergy-pair copy keys.** The 6 named synergy pairs (`classes.md` 2.2) modify an existing
   skill's numbers rather than adding a new displayed skill/ability, so no standalone UI string is
   needed for them; this avoids inventing a mechanic-adjacent lore surface the owner's instructions
   warn against ("no new lore system").
5. **`reward_area_3`/`reward_dungeon_2` left uncovered.** `content.md` 6.5 explicitly leaves these
   unbound (no IDs exist yet); there is nothing to key copy to, so none was written — not an omission.
6. **M1 `spec_*` rows kept, marked superseded.** Followed `content.md` 5.1's own precedent of marking
   the old specialization system superseded rather than deleting it, since old `BattleReport` rows may
   still reference it (`classes.md` section 9, migration point 3) and this document's job is copy, not
   data migration.
