## Finding 1: the week-budget worked example assumed the wrong dungeon floor count — corrected

`gear.md` section 7's worked week budget was written as a conditional ("if M2-31 supplies a
three-floor introductory dungeon") before M2-31 ran. M2-31 actually shipped `dungeon_aqueduct_depths`
as a **4-floor** dungeon (3 ordinary + 1 final boss) — confirmed both by `reports/engineering
M2-31.md`'s own description and directly by this task's simulation (`avgFloorsProcessed: 4`,
`clearRate: 1`, all 500 runs). Re-deriving section 4's own general formula at `n=4` instead of the
placeholder `n=3` changes every downstream number in the worked week budget:

| Quantity | Old text (`n=3` placeholder) | Corrected (`n=4`, actual) |
| --- | --- | --- |
| Per-clear: minutes / XP / gold / scrap / sigil / core / mean items | 9 / 32 / 80 / 8 / 2 / 1 / 1.5 | 12 / 40 / 100 / 10 / 2 / 1 / 1.75 |
| Per day (2 dungeon clears + 60 Old Road wins) | 760 gold / 304 XP / 16 scrap / 4 sigil / 2 core / 18 items / 78 min | 800 gold / 320 XP / 20 scrap / 4 sigil / 2 core / 18.5 items / 84 min |
| Per week | 5320 gold / 2128 XP (capped) / 112 scrap / 28 sigil / 14 core / 126 items | 5600 gold / 2240 XP (capped) / 140 scrap / 28 sigil / 14 core / 129.5 items |
| Balance after crafting basket (1500g/80 scrap/16 sigil/8 core) | 3820 gold / 32 scrap / 12 sigil / 6 core | 4100 gold / 60 scrap / 12 sigil / 6 core |
| Balance after recruiting heroes 4-6 (−1800 gold) | 2020 gold | 2300 gold |
| Day the full crafting basket becomes affordable | day 5 (scrap-bound at 16/day) | day 4 (scrap-bound at 20/day — reaches 80 scrap exactly) |

Sigils/cores per day/week are unchanged (they are flat per final-boss floor, not scaled by `n`), so
the epic-affordability finding ("affordable after four days' materials," core-bound) is unchanged.
I verified every number above by hand against `gear.md` section 4's formula and cross-checked the
totals arithmetically (e.g. `8*(4-1)+16=40`, `20*(4-1)+40=100`, `800*7=5600`) before editing the
document — this is a documentation correction, not a reward-table value change, so it required no
`packages/content` edit and no Gameplay Programmer task block (section 7 is pacing narrative; the
actual reward numbers consumed by code live in sections 2-5 and were already correct).

Applied directly in `design/game/economy/gear.md` section 7.

## Finding 2: no measurable team-building contrast at the only levels the harness tests — not an economy fix

M2.md's "done means" explicitly requires "a poorly built team (no healer, no tank, wrong formation)
loses or struggles against content a well-built team of the same average power clears." The existing
harness's two presets are built exactly to test this: `v2BalancedParty` (Vanguard/Herald tank with
Bulwark Call + Shield Bash, Cleric/Vanguard healer, Rogue/Arcanist DPS) vs. `v2GlassCannonParty`
(Rogue, Ranger, Arcanist — no taunt skill, no healing skill, same average level). Across all 500 runs
in 3 independent seed bases, **both builds won 100% of the time** against Old Road (level 5) and the
balanced build alone was tested at 100% clear rate against the 4-floor dungeon (level 8); the
glass-cannon build was consistently *faster* (fewer average rounds: 3.00-3.01 vs. 3.17-3.31), i.e. the
measured signal currently points the wrong direction from what the acceptance check wants.

This is not a number this role can fix. `baseline.md`/`gear.md` only control reward *amounts*; they do
not touch enemy HP/ATK/DEF, boss AI cadence, or row-protection/taunt behavior — those are
`content.md`/`combat.md` (Systems Designer's authored M2-22/M2-31 surface) and the engine
(`packages/game`, Gameplay Programmer). This mirrors M1-13's exact precedent above in this same
document: that task found boss-readiness pinned to a non-reward mechanic and declined to chase it
with a reward-table change, flagging it instead. I follow the same rule here: no `baseline.md`/
`gear.md` number is changed to manufacture contrast, and no content.md/combat.md edit is attempted
(outside this role's design authority over combat/content balance, and outside the explicit "send
Gameplay Programmer a task block for number changes" instruction, since the fix — if one is needed —
is an enemy/boss stat or AI change, not a reward number).

**What is and isn't shown:** `combat2.test.ts`'s "team-building lever" unit test (cited in
`reports/engineering/M2-26.md` check #10) already proves the taunt/row-protection mechanic works in
isolation. What the production-level simulation shows is that at the specific levels/content this
harness exercises (Old Road at level 5, the one dungeon at level 8), that mechanic's absence doesn't
yet cost the glass-cannon build anything — the content is not currently hard enough at those levels to
make the choice matter. Whether that's because players reach level 5/8 well past when Old Road/the
introductory dungeon are "current" content, or because the enemies themselves need more pressure, is a
content-difficulty judgment outside this task's evidence (it only has two fixed levels to look at).

This is recorded as an **open item for the Game Director (M2-30) and Systems Designer**, not acted on
here.

## Finding 3 (gap, not acted on): most of `gear.md` section 7's evidence requests can't be answered with the current harness

`gear.md` section 7 asks M2-28 to report: production distributions for fresh *and migrated* saves;
first-drop/rare/craft/reforge/epic timing; material/gold balances; overflow; unlocks and clear/fail
rates *by build and seed*; a legacy-gold-vs-material-constraint test; 1/3/5-hero group sweeps; offline
partitions; first week at 30/78/480 credited minutes/day; and guaranteed-material-failure recovery.

`scripts/simulate.mjs --mode=v2` currently supports exactly: a seed-repeatable reproducibility check,
a crafting/reforge reproducibility check, a 2-preset/fixed-level win-rate+rounds contrast, and a
single-preset/fixed-level dungeon clear-rate benchmark. It has no CLI-exposed level/party-size
parameter, no save-migration path (there is no `apps/server`/DB in this pure-engine harness at all —
migration is inherently a server-level concern M2-27 owns), no material/gold ledger accumulation
across simulated days, and no offline-partition timing model.

I did not fabricate numbers for these. I verified what I could analytically from documents I own
(the week-budget arithmetic in Finding 1, which is exact and closed-form) and I am sending one scoped
task block to the Gameplay Programmer (below) to extend the harness for the parts that need actual
simulation (hero-count sweep, dungeon win-rate for the glass-cannon build specifically, a
multi-day material/gold ledger). Retuning gear/XP/drop numbers against evidence that doesn't exist yet
would violate `gear.md`'s own "Retune only on that evidence" rule.
