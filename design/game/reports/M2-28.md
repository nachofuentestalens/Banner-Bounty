## Finding 2: no measurable team-building contrast at the only levels the harness tests — not an economy fix

M2.md's "done means" explicitly requires "a poorly built team (no healer, no tank, wrong formation)
loses or struggles against content a well-built team of the same average power clears." The existing
harness's two presets are built exactly to test this: `v2BalancedParty` (Vanguard/Herald tank with
Bulwark Call + Shield Bash, Cleric/Vanguard healer, Rogue/Arcanist DPS) vs. `v2GlassCannonParty`
(Rogue, Ranger, Arcanist — no taunt skill, no healing skill, same average level). Across all 500 runs
in 3 independent seed bases, **both builds won 100% of the time** against Old Road (level 5) and the
balanced build alone was tested at 100% clear rate against the 4-floor dungeon (level 8); the
glass-cannon build was consistently *faster* (fewer average rounds: 3.00-3.01 vs. 3.17-3.31), i.e. the
measured signal currently points the wrong direction from what the acceptance check wants.

This is not a number this role can fix. `baseline.md`/`gear.md` only control reward *amounts*; they do
not touch enemy HP/ATK/DEF, boss AI cadence, or row-protection/taunt behavior — those are
`content.md`/`combat.md` (Systems Designer's authored M2-22/M2-31 surface) and the engine
(`packages/game`, Gameplay Programmer). This mirrors M1-13's exact precedent above in this same
document: that task found boss-readiness pinned to a non-reward mechanic and declined to chase it
with a reward-table change, flagging it instead. I follow the same rule here: no `baseline.md`/
`gear.md` number is changed to manufacture contrast, and no content.md/combat.md edit is attempted
(outside this role's design authority over combat/content balance, and outside the explicit "send
Gameplay Programmer a task block for number changes" instruction, since the fix — if one is needed —
is an enemy/boss stat or AI change, not a reward number).

**What is and isn't shown:** `combat2.test.ts`'s "team-building lever" unit test (cited in
`reports/engineering/M2-26.md` check #10) already proves the taunt/row-protection mechanic works in
isolation. What the production-level simulation shows is that at the specific levels/content this
harness exercises (Old Road at level 5, the one dungeon at level 8), that mechanic's absence doesn't
yet cost the glass-cannon build anything — the content is not currently hard enough at those levels to
make the choice matter. Whether that's because players reach level 5/8 well past when Old Road/the
introductory dungeon are "current" content, or because the enemies themselves need more pressure, is a
content-difficulty judgment outside this task's evidence (it only has two fixed levels to look at).

This is recorded as an **open item for the Game Director (M2-30) and Systems Designer**, not acted on
here.

### Resolved: 1/3/5 heroes × 30/84/480 credited minutes/day

The ledger matrix above is the full 3×3 grid `gear.md` section 7 asks for, at level 8 (the
"established party" level this section's own worked week budget uses). Two findings:

- **Old Road income (gold, items, XP-per-participant) does not depend on hero count at all**,
  only on minutes/cycles spent — 1-hero and 3-hero and 5-hero rows are byte-identical at 30 and
  480 min/day (no dungeon attempted). This matches `gear.md` section 3's rule that Old Road gold
  is per-account and item probability is per-cycle, not per-hero; it is not a bug.
- **Dungeon eligibility does depend on hero count**: the 1-hero party fails all 14 dungeon
  attempts at the 84-min/day rate (0/14 clears) while the 3-hero and 5-hero parties clear all 14
  (14/0), with identical per-clear rewards. This is a genuine, previously-unmeasured team-building/
  party-size signal — a lone hero cannot clear `dungeon_aqueduct_depths` at level 8 even though a
  same-level 3- or 5-hero party clears it every time. It is recorded here as evidence, not acted
  on: whether solo dungeon-locking is intended is a Systems Designer/Director scope call, not an
  economy-table number, and no `gear.md`/`baseline.md` reward value is changed to react to it.

This resolves the "1/3/5-hero groups" and "first week at 30/84/480 credited minutes/day" asks in
full, at level 8. It does not cover other levels (the harness holds level fixed for the whole
ledger run; rerunning `--level=<n>` samples a different fixed-level point, same limit the matrix
task already documented) — reported as a bounded result, not a universal one.

Overflow is measured directly in every ledger row above (e.g. 28 items converted at the 100-slot

### Still open: purchases (spending), fresh-vs-migrated progression, offline partitions, failure recovery

These four `gear.md` section 7 asks remain unanswerable with the current harness, for the specific
reasons below (not fabricated, not assumed):

1. **Purchases/spending.** `runV2Ledger` (`scripts/simulate.mjs`) only accumulates gold/materials
   from Old Road wins and dungeon clears; it never calls `resolveCraft`, `resolveReforge`, or the
   recruitment cost. There is no CLI flag to schedule a craft/reforge/recruit action on a given day.
   Missing capability: a ledger-mode option to spend on a recipe or recruit a hero on a chosen day
   and deduct/validate against the running balance.
2. **Fresh vs. migrated save progression.** The harness is pure-engine (`packages/game`/
   `packages/content`); it has no `apps/server`, no database, and no migration entry point to call
   — migration is a server-level concern (M2-25/27's contracts), confirmed by `grep -i migrat` over
   `packages/` returning only type/contract references, no runnable migration path. Missing
   capability: a server-backed (or server-mocked) harness mode that can apply the documented
   migration rules (`gear.md` section 6) to a legacy save and compare its post-migration state to a
   fresh account under the same activity schedule.
3. **Offline partitions.** `scripts/simulate.mjs` has no offline/partition concept at all (confirmed:
   no match for `offline`, `partition`, `credited` outside this ledger's own day-granularity loop).
   The existing ledger only models whole in-session days, not a split session with an offline gap
   credited against the eight-hour cap mid-day. Missing capability: a ledger option to split a day's
   credited minutes across an online segment and an offline segment with its own cap/clock rules.
4. **Guaranteed-material failure recovery.** Since the ledger never spends materials (see #1), it
   cannot simulate running out of materials mid-craft and recovering by playing more. Missing
   capability: the same spend action needed for #1, plus a scripted "insufficient materials, reject
   without spending" case drawn directly from `gear.md` section 5's own rejection rule.

No number in `baseline.md`/`gear.md` is retuned against these four items, consistent with
`gear.md` section 7's "retune only on that evidence" rule — there is no evidence yet to retune
against. A scoped harness-extension task block for Gameplay Programmer, covering all four gaps
together, is included below (the matrix task already covered levels/heroes/ledger-days; this is
the remaining piece).
