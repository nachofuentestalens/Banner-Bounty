## Acceptance checks

**1. Tables/formulas have explicit units, probabilities summing correctly, rounding, caps and losses; XP per hero and level-up stat growth are unambiguous.**
- Check: `baseline.md` section 1 gives `xpToNext(level) = 15 * level`, an explicit integer formula
  with a cumulative-XP table for levels 1-10, a stated level-10 cap (further XP in the same
  transaction is discarded, not banked), and an explicit carry-remainder level-up loop that handles
  multi-level jumps in one large batch (relevant given the 480-cycle, 8-hour settlement batch in
  `contracts.md`).
- Check: section 2 states XP (`4`, per hero, per won cycle) and gold (`10`, per account, per won
  cycle) as flat integers with explicit units ("XP", "gold"), and explicitly zeroes all three reward
  types on a lost cycle, citing `first-playable.md`'s "a loss consumes the cycle and awards no
  loot/XP/gold."
- Check: section 4's drop/affix probabilities are verified summing to 1 in-document: `0.75` (no
  drop) `+ 0.1667` (common) `+ 0.0833` (uncommon) `= 1.0`; the 9-definition and 3-affix rolls are
  stated as independent uniform draws (`1/9` and `1/3` each) and verified independent of each other.
  I re-added these by hand during this task: `0.25 * 2/3 = 0.16666...` and `0.25 * 1/3 = 0.08333...`,
  summing with `0.75` to `1.0` within rounding presentation.
- Check: rounding is explicit throughout — "floor (truncating) integer division unless stated
  otherwise" (document header), `ceil(...)` used only for the pacing *estimates* in section 7 (never
  inside a reward formula, where floor is used exclusively), and the affix-threshold comparison note
  in section 4 flags comparing against the exact rational boundary rather than a rounded decimal.
- Check: level-up stat growth itself is not re-specified here (it is `combat.md` 1.1's `statAtLevel`,
  already frozen); section 1 is explicit that it only fixes *how much XP* produces a level-up, not
  what a level changes mechanically, avoiding a second, possibly-conflicting growth table.
- Result: **pass**.

**2. Show expected ordinary elapsed time to first gear, level 3 and boss readiness; label estimates pending simulation.**
- Check: section 7's table gives all three milestones against `first-playable.md`'s hypothesis
  ranges (~5 min / 10-15 min / 20-40 min) with hand-derived point estimates (~4 min / ~12 min /
  ~23-38 min), each traced from the section 1/2/4 formulas, not invented separately.
- Check: the document's header and section 7's lead paragraph both explicitly label these as
  "hand-derived point estimates... not a simulation result," name M1-12/M1-13 as the tasks that must
  confirm them against the production engine and fixed seeds, and the boss-readiness band includes
  an explicitly-labeled "rough (hand-estimated, not simulated)" feasibility trace rather than
  presenting it as validated.
- Result: **pass**.

**3. Specify the 100-unequipped-item limit and deterministic overflow behavior without deleting equipped gear.**
- Check: section 6 states the `100` cap applies only to unequipped instances, that equipped items
  never count toward it and are never touched by overflow, gives a documented gold-conversion table
  (common `5` gold, uncommon `9` gold) satisfying `first-playable.md`'s "documented gold amounts,"
  and specifies strict cycle-order processing within a multi-cycle batch so the overflow check is
  never run against a stale count — matching `contracts.md`'s "no separate pass that could run
  against a stale count" requirement word-for-word in intent.
- Check: the batch-determinism argument explicitly relies on `contracts.md`'s `active_expedition`
  equip/unequip lock (no mid-batch equip is possible) to justify that the running unequipped count
  only ever increases within one settlement, closing the one gap that could otherwise make
  overflow order ambiguous.
- Result: **pass**.

**4. Specify non-exploitable one-time boss reward and zero arena rewards; match offline cycle/cap semantics.**
- Check: section 3 ties the one-time reward to `BossClaim.claimedAt`'s atomic `null -> serverNow()`
  transition already fixed by `contracts.md`, states every subsequent win grants zero of all three
  reward types (only a report), and states a loss never mutates the claim flag — so repeated
  challenges (free, no entry cost) cannot farm gold/XP/items, which is the exploit `first-playable.md`
  and backlog's "non-exploitable" language are guarding against.
- Check: section 5 states arena grants zero gold/XP/items regardless of result, matching the
  backlog's explicit "zero arena rewards" acceptance line and `first-playable.md`'s no-shop/no-crafting
  minimalism.
- Check: section 2/6/8 reuse `contracts.md`'s existing offline cycle/cap semantics (60-second cycle,
  8-hour/480-cycle cap, `frozenLoadout` for combat vs. live `level`/`xp` for rewards) rather than
  inventing competing numbers; the one new piece of behavior this document adds on top of that
  semantics — multi-level-up-in-one-batch and in-batch overflow ordering — is specified in sections 1
  and 6 precisely because a 480-cycle batch exercises both in ways a single cycle would not.
- Result: **pass**.

## Unresolved issues / limitations

- Section 7's pacing numbers are hand-derived from the reward formulas plus one hand-estimated,
  unequipped/unspecialized boss trace at a single level (5). They are not a swept simulation across
  seeds, builds, equipment states, or specialization choices — M1-12 (production simulation engine)
  and M1-13 (evidence-based tuning, owned by this same role) are the explicitly scoped next steps to
  validate or correct these numbers once `packages/game` exists. This task's brief itself requires
  only that estimates be labeled pending simulation, not that they be simulation-verified.
- The flat `4` XP/cycle and `10` gold/cycle constants, and the `25%`/`1/3` drop/affix probabilities,
  are first-pass values chosen to land inside `first-playable.md`'s pacing hypotheses by hand
  arithmetic; they are plausible but unvalidated starting points, exactly the kind of number M1-13 is
  scoped to tune from evidence rather than accept as final.
- Whether a mid-expedition level-up's stat growth takes effect in the same expedition's remaining
  cycles or only the next one is explicitly left to M1-02/M1-08 per `contracts.md`'s own framing;
  this task does not resolve it and does not need to, since it only fixes XP *amounts*, not stat
  growth or its timing.
- `node scripts/dashboard.mjs status` does not resolve in this worktree (see Commands run); this is
  a dashboard/worktree environment limitation, not a defect in this task's deliverable, and matches
  limitations other agents have already flagged for this same worktree setup.
