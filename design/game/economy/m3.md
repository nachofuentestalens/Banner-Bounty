## 2. G3 — duration model: candidate formula and provisional bands

### 2.1 Formula candidate

`m3-systems.md` §3/§12 requires nominal expedition duration to be "a deterministic positive
integer function of resolved combat length," with `2000 ms/round` offered only as a **measurement
candidate**, not frozen. The candidate formula is:

```
nominalDurationMs(battle) = resolvedRounds(battle) * 2000
```

`resolvedRounds` is the actual round count combat.md §8 produces for that battle's frozen build/
seed (integer, 1-100). This differs fundamentally from the legacy Old Road model (`baseline.md`
§2, `gear.md` §4): a fixed 60-second wall-clock cycle regardless of how fast combat actually
resolves. Dungeon floors are explicitly **not** changed by this candidate: `m3-systems.md` §3/§7
retains 180 seconds/floor (720 seconds max/4-floor clear) independent of round count.

### 2.3 The open risk this candidate creates — not resolved here

At `2000 ms/round`, an Old Road battle's nominal duration is **6.0-10.6 seconds** (3-5.3 rounds),
roughly **6-10x shorter** than the legacy fixed 60-second cycle every existing minute-band
("~5 min first drop," "10-15 min level 3," "84 credited minutes/day") is built on. `m3-systems.md`
does not specify whether a travel/setup floor exists in addition to combat length, or whether
per-battle reward amounts are re-derived for the shorter nominal duration. Inventing either answer
here would be a fabricated measurement. This document therefore carries two explicit scenarios
forward to M3-05/M3-10 instead of picking one:

- **Scenario A — combat-length-only** (the formula in §2.1 with no floor). Credited-minutes-per-day
  translate to roughly 6-10x more battles than the legacy model at the same clock time; every
  existing per-cycle reward number becomes 6-10x more frequent unless re-derived. This is the
  literal reading of `m3-systems.md` §3.
- **Scenario B — combat-length plus a retained 60-second-equivalent floor**, used below as the
  **transitional default for all worked numbers in this document**, because it is the only scenario
  the existing harness (`--mode=v2ledger`) actually measures today (it still runs 60-second Old
  Road cycles internally) and because it preserves every already-evidenced M1/M2 pacing number
  without a fabricated multiplier.

**Required before freezing either scenario (M3-05/M3-10):** measure `resolvedRounds` distributions
for the actual M3 content (new classes/specializations/races, Cinder Archive) once M3-07 ships it,
then decide with the CTO whether a floor is part of the production contract. Until that decision,
Scenario B is the working assumption; Scenario A's 6-10x acceleration is flagged as a real risk to
re-check, not dismissed.

### 2.4 Level-3 boss readiness is preserved under both scenarios

`m3-systems.md`'s policy line is explicit: "preserve the owner's early level-3 boss readiness."
Readiness is an **XP-gate event** (level 3 reached at exactly 45 cumulative XP = 12 Old Road wins,
per `baseline.md` §7/`tuning.md`'s M1-13 decision, reconfirmed unchanged by M2-28/this task — no
XP/gold number changes in M3), not a wall-clock constant. The duration-model choice in §2.3 changes
only how many *minutes* those 12 cycles take, never the 12-cycle count itself:

| Scenario | Wall-clock time for 12 cycles to reach level 3 |
| --- | --- |
| Legacy 60s/cycle (current baseline.md §7 "10-15 min" band) | ~12 minutes — unchanged, within band |
| B (floor retained) | ~12 minutes — unchanged, within band |
| A (combat-length-only, no floor, ~3.3-5.1 rounds/battle) | ~72-127 seconds |

Scenario A would move level-3 readiness far below the existing 10-15 minute band. Since the band
itself was a hand-estimate `tuning.md` already treats as secondary to the measured cycle-count
(which is what "readiness" actually means per that decision), this is reported as a consequence to
confirm, not a violation to immediately fix: if Scenario A is chosen, the 10-15 minute text in
`baseline.md` §7 needs a corrected band the same way M1-13 corrected the boss-readiness row, once
M3-05 decides the production duration contract.

## 5. Catch-up measurement specification

**Definition (reusable across M1/M2/M3):** a catch-up measurement is a repeatable benchmark of one
authoritative settlement transaction covering the maximum eligible offline window (eight hours),
run for at least 20 repetitions, reporting min/median/p95/max duration in milliseconds plus the
exact CPU model, core count, Node version, OS/arch, and the number of discrete events (cycles or
battles) settled. **Target: p95 duration under 2000 ms** on stated hardware. Evidence required
before accepting any tuned value that changes settlement volume (e.g. a shorter nominal battle
duration under Scenario A, §2.3, which could raise the number of battles per 8-hour window by
6-10x): rerun this exact benchmark shape against the new volume and confirm p95 remains under
target; if it does not, this is an engineering performance question (M3-05/M3-07), not a reward-
table one, following the same non-reward-table-fix rule `tuning.md`'s M1-13/M2-28 decisions set.

**Current evidence (§4 run #6):** the existing `--mode=catchup` benchmark (480 fixed 60-second
cycles — the legacy model) measures p95 8.01 ms, far under the 2000 ms target, on
Intel Core i7-14700K x28 / Node v22.14.0 / win32-x64. This is reused as the closest available
baseline; it does **not** yet exercise the combat-length-based duration model (§2.1) or any M3
content, because neither exists in the engine yet. **Required before M3-05 freezes the production
duration contract:** rerun this same benchmark shape against the actual M3 settlement loop once
M3-07 ships it, at both Scenario A and Scenario B's implied event volumes, and record p95 against
the same under-2-second target with the same hardware-reporting format as above.

## 6. Tactical measurement protocol — 32 paired seeds per encounter/build pair

Not yet executable (§0): no new class, specialization, race, or Cinder Archive content exists in
`packages/content`/`packages/game`. This section specifies the exact protocol M3-07/M3-10 must run,
reusing the existing harness's paired-build pattern (`v2BalancedParty`/`v2GlassCannonParty`) rather
than inventing a new one.

**Protocol:**

1. **Pair selection.** For each of the following pairs, run the matrix below: (a) existing
   Vanguard/Herald-tank balanced party vs. glass-cannon party against Cinder Archive floors 1-4
   (the "no-new-class" counterexample `m3-systems.md` §7 requires); (b) a Warder-included party vs.
   the same glass-cannon party against Cinder Archive; (c) a Weaver-included party vs. the
   glass-cannon party against Cinder Archive; (d) one party per primary specialization choice
   (16 total) built around the skill that specialization modifies (e.g. `m3spec_warder_anchor`
   party includes Brace slotted) vs. its unmodified-specialization twin, against the existing
   dungeon (isolates the specialization's effect, not the new dungeon's); (e) one party per race
   (`race_vesper`/`race_cairn`/`race_serein`) with identical class/level/gear, against Old Road at
   level 5 (isolates the race tradeoff).
2. **Seeds.** At least 32 independent seeds per pair (e.g. seeds 1-32), each run once per side of
   the pair under identical seed (paired, not independently randomized) so any difference is
   attributable to the build, not seed variance.
3. **Equal budgets.** Both sides of a pair share identical hero level, equal total gear budget
   (same rarity distribution and affix count, not necessarily identical affix IDs unless isolating
   one specific stat), identical formation unless formation is the isolated variable, and recorded
   initial stats/skills/slots exactly as `m3-systems.md` §7/S08 requires.
4. **Reported metrics per pair:** clear rate (wins/32), mean and distribution of rounds-to-clear
   (or rounds-to-loss), normalized surviving HP (`floor(100*remainingHP/maxHP)` per surviving hero,
   averaged across the party, per `m3-systems.md` §9's existing HP-normalization convention), and
   survivor count. Report every seed's result, not only the aggregate, so a counterexample (a seed
   where the "expected" build loses or the "unexpected" build wins) is visible rather than averaged
   away. `m3-systems.md` §7 explicitly requires at least one counterexample to be surfaced, not
   hidden by aggregation.
5. **No reward-table response to a balance finding.** If a pair shows no contrast (as M2-28 found
   at level 8 for the existing dungeon) or an unexpected dominant pairing, that is routed to
   Systems Designer/content.md or combat.md, never resolved by editing a reward number here — the
   same rule `tuning.md`'s M1-13/M2-28 decisions already established, restated here because
   `m3-systems.md` repeats the same risk for new content.

**Command shape to extend when content lands:** `node scripts/simulate.mjs --mode=v2 --dungeon=cinder_archive --heroes=<pair> --seed=<1..32> --runs=1 --level=<intended entry level>` (flag names illustrative; exact CLI surface is Gameplay Programmer's to add, matching the existing `--level`/`--heroes` pattern already in the harness).

## 7. Respec cost/cooldown reconciliation with M3-03

`m3-systems.md` §6 sets the provisional primary-respec formula `100*L gold + 5*L scrap +
(L>=5 ? 1 : 0) sigil`, cooldown 24 server hours per hero, and explicitly allows M3-04 to amend the
cost/cooldown before M3-05 freezes contracts. Checked against this task's measured 7-day, 3/5-hero
ledger (§4 run #4/#5: 5835 gold / 140 scrap / 28 sigil / 14 core from zero, 84 credited min/day):

| Level | Formula cost | Share of one week's income |
| --- | --- | --- |
| L1 | 100 gold, 5 scrap, 0 sigil | <2% gold, <4% scrap |
| L5 | 500 gold, 25 scrap, 1 sigil | ~9% gold, ~18% scrap, ~4% sigil |
| L10 | 1000 gold, 50 scrap, 1 sigil | ~17% gold, ~36% scrap, ~4% sigil |

**Decision: keep the formula unchanged as the provisional default.** A single respec at any level
is affordable within one week's income without starving the crafting basket (`gear.md` §7) for
more than a few days. The **24-hour cooldown**, not the gold/scrap cost, is the practical limiter
on respec frequency: at most 7 respecs/week per hero, which at L10 would consume 350 scrap/week —
more than the measured 140 scrap/week income — so a player cannot "live" on repeated respecs
without the cooldown already capping that before cost does. This matches `m3-systems.md` §6's "no
escalation or lifetime cap" instruction (the cooldown is the only throttle, by design) and needs no
amendment. **Not measured:** actual player respec frequency/cadence (no behavioral data exists
pre-launch); this is an affordability check against measured income, not a claim about how often
players will actually respec.

Secondary-only switching stays free/no-cooldown per `m3-systems.md` §6; no economy number applies
to it, so there is nothing for this document to tune there.

## 8. Season/tournament rewards — recognition-only, confirmed

`m3-systems.md` §8/§9 already specifies season/tournament rewards as a season-labelled recognition
title only (rank 1 standings title, tournament champion title), explicitly "no gold, XP, items,
materials, stats, discounts or ongoing buffs" and "no extra season points" for the tournament. This

currency/items or escalating stats" requirement by confirming M3-03's existing specification rather
than adding a new one.

## 9. Fixed-level income vs. actual progression — explicit distinction

Every ledger number in §4 (runs #3-5) is a **fixed-level income scenario**: level held constant at
8 for the whole simulated week, no XP-driven leveling, no equipment acquired/equipped mid-run,
empty starting bag. This answers "how much does a level-8 party earn per day," not "how does a
fresh level-1 party actually progress to level 8." `m3-systems.md` §12 explicitly requires both:
"measure fresh/migrated progression, not fixed-level income alone." The **actual progression**
side is answered by the existing per-cycle XP math already validated in `baseline.md` §7/`tuning.md`
(12 cycles to level 3, 38 to level 5, 105 to level 8, 169 to level 10 — unchanged by M3, since no
XP number changes) combined with §2's duration-model bands for wall-clock conversion. The gap is a
single integrated simulation that starts at level 1, zero gear, and plays forward through both
leveling *and* earning *and* a dungeon unlock in one run — the harness does not do this (same gap
as M2-28 Finding 3, carried forward unresolved). Requesting that harness extension is listed in
§10's next task rather than fabricated here.
