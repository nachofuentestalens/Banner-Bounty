# M2-01: Amend contracts for second expedition area — evidence report

Date: 2026-10-19 · Owner: CTO · Task ID 25640c47-70ba-49aa-99bd-96c0a270f204

## What changed

Appended a new, clearly delimited `## M2-01 addition: second expedition area (M2 amendment, additive only)` section to `design/studio/contracts.md`, after the existing "Open items for downstream tasks" section. Nothing above that heading — the frozen M1-01 surface — was edited, reordered, or reworded.

The amendment adds:

1. **New entity** `Area { areaId, name, unlockRequirement: { kind, value? } }` — server-owned reference data, parallel to `packages/content`'s existing static definitions, not a per-account row.
2. **Additive field on `Account`**: `selectedAreaId`, with an explicit migration rule (existing M1 accounts default to the starter area's `areaId` at migration time).
3. **Additive field on `Expedition`/`ExpeditionViewDTO`**: `areaId`, frozen at `/expedition/start` exactly like `rulesVersion` — copied from `Account.selectedAreaId` at that instant, immune to later reselection until the run ends.
4. **One additive field on an existing M1 endpoint**: `GET /account/state` response gains `selectedAreaId`. This is the only touch to an M1-01 endpoint, and it is purely additive (new field, no field removed/renamed, no new error code).
5. **Two new endpoints**:
   - `GET /areas` — session-only, read-only, lists `AreaSummaryDTO { areaId, name, unlocked, isSelected }`.
   - `POST /area/select` — session-only, sets `Account.selectedAreaId`, following the canonical revision/idempotency protocol unchanged. Blocked by `active_expedition` (mirrors the equip/unequip/specialization lock) so a mid-run area switch can never desync from the already-frozen `Expedition.areaId`.
6. **Package-boundary note** confirming no new cross-package import edges: `Area` content lives in `packages/content`; selection/unlock evaluation lives in `apps/server`; `packages/contracts` exports the new DTOs/schemas under the existing rules.

## Why these choices

- **`/expedition/start`'s payload is untouched.** Area is selected ahead of time via `/area/select`, not passed to `start`. This means the one endpoint most central to M1 (expedition start) needs zero payload/behavior change — only its response DTO gains an additive field, following the exact precedent M1-08 already set for `wins`/`losses`/`outcomes`/`overflow`/`recentCycles`. This was the main lever for satisfying "do not redesign or break any existing M1 endpoint."
- **Area selection is locked by `active_expedition`, not by its own new error code.** Reusing the existing precondition category instead of inventing a new one keeps the error-code enum (`validation | unauthenticated | forbidden | not_found | conflict | active_expedition | internal`) unchanged, and keeps the mid-run lock semantically consistent with the existing equip/unequip/specialization examples (Worked example 9).
- **`not_found` for unknown `areaId`, `forbidden` for known-but-locked.** This mirrors two already-established patterns in the same document: `arena/challenge`'s `not_found` for an unknown `snapshotId`, and `forbidden`'s use elsewhere for "this reference is valid but access is denied" rather than "this reference doesn't exist."
- **`Area.unlockRequirement` is deliberately left opaque (`{ kind, value? }`).** Fixing the exact unlock rule (hero-level threshold vs. boss-clear gate vs. something else) is a content decision, not a contract shape decision — scoping it out keeps this amendment a pure contract/transport change and hands the actual rule to Systems Designer (M2-02), who owns area-2 content.
- **`BossClaim` needs no change.** It is already keyed by `(accountId, bossId)`, so a second area with its own boss is already representable under the M1 shape — confirmed explicitly in the amendment so M2-02/M2-05/M2-06 don't block on re-deriving this.
- **Migration default for `selectedAreaId`.** Every M1 save predates this field; the amendment requires the migration to set existing accounts to the starter area's `areaId` so `/account/state` never returns a missing/null value. The exact starter `areaId` constant is left to M2-02 (it doesn't exist yet — M1 never named areas).

## Open question for Systems Designer (M2-02)

Before specifying area-2 content, M2-02 must pin down:
1. Concrete `areaId` values, including which one is the "starter" area (needed for the M1-save migration default on `Account.selectedAreaId`).
2. The `unlockRequirement.kind` values this contract leaves opaque, and their exact evaluation rule (e.g. hero-level threshold vs. a specific boss clear vs. something else).
3. Confirmation that no `BossClaim` shape change is needed for a second area's boss — already true under the existing `(accountId, bossId)` key, stated here so M2-02 doesn't have to re-derive it.

None of these are contract blockers; they are content decisions within the shape fixed by this amendment.
