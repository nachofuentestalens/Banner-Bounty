## Final pass (4 fixes)

A second, smaller review pass requested four fixes, all applied to `contracts.md`:

1. **Public-endpoint exception list (Conventions line).** The cookie-requirement sentence previously named only `health` and session selection as exceptions, omitting the two public arena-snapshot reads added in the first revision pass. Now lists all four: `GET /health`, `POST /dev/session/select`, `GET /arena/snapshots`, `GET /arena/snapshots/:snapshotId`.
2. **"Atomic transaction boundaries" vs. the canonical protocol.** The paragraph previously said the simulation "runs in memory first" without saying relative to which protocol step, and didn't state what happens if state drifts during that out-of-transaction work. Rewrote it to place the simulation explicitly before protocol step 1 ("Begin transaction"), and to state that step 4's revision recheck inside the transaction is therefore also a check that nothing the simulation read has changed since — a mismatch returns `conflict` and discards the precomputed result, requiring the client to refetch and resimulate rather than just retry the commit.
3. **Ownership-rule sentence (line 31).** Rewrote the dense, parenthetical-heavy sentence into three plain sentences: the server resolves `accountId` from the cookie only; `HeroId`/`ItemInstanceId` ownership is checked before any mutation; `snapshotId` is the one explicit exception since cross-account snapshot reads are allowed by design.
4. **Example 10 vs. the M1-02/M1-08 open item.** Example 10 previously asserted a specific answer ("a level gained mid-run does not retroactively change that run's combat inputs") that contradicted the adjacent open item, which defers that exact question to M1-02/M1-08. Reworded example 10 to state only what this contract actually fixes (level/xp mutable mid-run; equipment/specialization frozen until stop) and to explicitly leave the stat-timing question open rather than answering it.

## Revision pass (review findings 1-6)

A review of the initial freeze raised six findings; all six are fixed in this revision of `contracts.md`:

1. **Error codes per endpoint.** Every endpoint now lists its complete error set explicitly (including `unauthenticated` and `internal` on every applicable endpoint, not implied). Added a line in the "Endpoints" section stating this completeness rule so no future addition silently omits a code.
2. **Public vs session-only data, plus a snapshot-by-ID endpoint.** Renamed the split to "Public" / "Session-only" for clarity and added the missing `GET /arena/snapshots/:snapshotId` endpoint — the prose previously described "fetched by ID for opponent preview" without a corresponding endpoint definition.
3. **Whether a no-op settle changes revision.** Resolved: a settlement that credits 0 cycles makes no persisted change, so it does **not** increment revision (previously the text ambiguously said both "bumps revision by 0 changes" and implied a receipt at a new revision). The protocol's step 6 and worked example 1 now state this explicitly and consistently with each other and with the "Atomic transaction boundaries" paragraph.
4. **Stored-result lookup before the expedition-lock check.** The canonical protocol now states the idempotency-receipt lookup (step 2) always runs before any precondition check, including `active_expedition` (step 3) — reversing the previous (wrong) ordering implied in worked example 9, where the lock was described as checked "before the idempotency/revision logic." A retried request that already succeeded returns its stored result even if the account later started an expedition.
5. **One stated transaction order.** The "Revision & idempotency protocol" section is now explicitly the single canonical order referenced by every endpoint and every worked example; no section restates or contradicts it. Worked examples 1 and 9 were rewritten to cite the canonical steps instead of describing their own ordering.
6. **Ownership/report-code wording.** Rewrote the `GET /battle-reports/:reportId` entry to state the `not_found`-for-both-missing-and-foreign-ID decision once, cleanly, with the reasoning (avoids distinguishing "exists but not yours" from "doesn't exist"), and to note why other endpoints keep `forbidden` distinct (no ID-enumeration secret at stake for owned-roster IDs).
7. **XP mid-expedition vs. frozen loadout.** Added worked example 10: hero `level`/`xp` are not frozen and can change via settlement rewards while an expedition runs; only `equipment`/`specializationId` are frozen until `stop`. Crossing level 3 mid-run makes a hero spec-eligible but the `hero/specialization` call still returns `active_expedition` until the expedition stops. Added a corresponding line to "Open items for downstream tasks" deferring the exact XP curve and whether stats re-scale mid-run to M1-02/M1-08 — this is a timing/shape clarification, not a new numeric commitment.

## Decisions recorded in this task (routine, within documented scope)

- Party reordering is **not** blocked during an active expedition (only equip/unequip/specialization are); the frozen loadout used by the running expedition is a separate snapshot from live `partyOrder`, so reordering has no effect until the next expedition start. This was underspecified in architecture.md ("Equip/reorder/spec changes are refused" suggested reorder might also be locked); I resolved it toward the narrower read consistent with "frozen party loadout" already capturing order at start, and recorded the reasoning inline in `contracts.md` rather than leaving it ambiguous for M1-08/M1-10.
- Cross-account battle-report access and non-existent report IDs both return `not_found` (not `forbidden`) to avoid ID-enumeration distinguishing — consistent with architecture's "reject cross-account IDs" without specifying the exact error code. Other ownership failures (hero/item/party) keep `forbidden` since no enumeration secret is at stake there (finding 6).
- `subCycleRemainderMs` is retained as a schema field (always 0 in M1) rather than removed, to avoid a migration if a future milestone shortens cycle length below 60s; this is a forward-compatibility note, not new scope.
- Idempotency-receipt lookup is the universal first step of the transaction protocol, ahead of every precondition including `active_expedition`; a request whose effect was already committed is never re-evaluated against newer conditions (finding 4).
- A zero-credit settlement does not increment account revision, since nothing persisted actually changed; it still writes a receipt so retries are safe (finding 3).
- Hero level/xp are mutable mid-expedition via settlement rewards; only equipment/specialization selection stay frozen until the expedition stops (finding 7).
