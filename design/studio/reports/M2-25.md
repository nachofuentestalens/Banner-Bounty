# M2-25: Amend contracts for roster, party of 5, skills, crafting, dungeons and replays — evidence report

Date: 2026-10-21 · Owner: CTO · Task ID 313da1bd-c298-4187-a9eb-a86bd34347e0

## Scope

Amended `design/studio/contracts.md` with a new "M2-25 addition" section, additive to the frozen M1-01
surface and the M2-01 addition, covering every system M2.md's scope items 3-5 require contracts for:

- Hero recruitment and a roster larger than the party cap (`POST /hero/recruit`).
- Dual class and skill loadout (`POST /hero/secondary-class`, `PATCH /hero/loadout`).
- A party of up to 5 with front/back formation (`PartyFormation`, `PATCH /party/formation`, replacing
  `PartyOrder`/`PATCH /party/order`).
- Crafting and reforging (`POST /craft`, `POST /reforge`), consuming `gear.md` section 5's exact rules.
- Dungeon runs (`DungeonRun`, `POST /dungeon/start`, `POST /dungeon/settle`, `POST /dungeon/stop`),
  including a floor-settlement algorithm specializing the existing offline-settlement algorithm with
  gear.md section 4's early-termination-on-loss rule.
- The battle-replay event schema (`BattleUnitDTO`, `BattleEventDTO`), formalizing `combat.md` section
  8.6's logical shape as the actual `packages/contracts` TypeScript it leaves open, covering every unit
  on both sides, HP, statuses (with duration), and a per-action event (actor/skill/target/amount/
  crit/dodge/death).
- A frozen 10-step migration procedure from M1 saves, formalizing `classes.md` section 9 and `gear.md`
  section 6 into exact field renames/derivations rather than prose.

## Decisions recorded (routine, within documented scope — AGENTS.md rule 4)

1. **`Hero.specializationId`, `PartyOrder`, and `ItemInstance.affixId` are replaced, not extended.**
   Their M1 shapes (one of 2 specs; a fixed 3-tuple; one nullable affix) cannot express dual-class/
   skill-loadout, a 5-slot formation with nulls, or ordered multi-affix rarity. Pre-launch (no real
   players on M1 saves) makes a clean replacement acceptable instead of a compatibility shim; each
   replacement has an explicit migration step. Every other M1 entity/endpoint is untouched.
2. **`PATCH /party/order` is removed in favor of a new `PATCH /party/formation`**, rather than reusing
   the path with a changed payload shape — reusing it would silently break the documented contract
   under the same name, which the existing document's own convention (explicit, named, dated changes)
   argues against.
3. **New `ErrorCode` value `active_dungeon`**, symmetric with `active_expedition`: expedition-start and
   dungeon-start each check for *either* activity being active (gear.md section 4's "only one
   progression activity may run per account"), returning whichever is actually blocking.
4. **Formation reorder is not locked by `active_expedition`/`active_dungeon`**, mirroring the M1-01
   decision on `/party/order` (classes.md section 3: formation only affects future activity starts).
   Secondary-class assignment and skill-loadout changes **are** locked by both, per classes.md 4.2's
   explicit "same lock timing as loadout changes."
5. **Reforge's recipe is server-derived from the item's own rarity, not client-supplied** — the payload
   has no `recipeId` — closing an under-payment vector a naive "client names the recipe" design would
   open.
6. **Secondary-class assignment accepts no `null`** (cannot be un-assigned once set, only switched to a
   different class) since nothing in `classes.md` requires clearing it and "no secondary" is already
   reachable (every hero starts there). Assigning a secondary does not auto-fill the loadout with its
   skills — loadout and secondary-class choice stay independently settable.
7. **`DungeonRun` is a single terminating run per account, not a repeating cycle like `Expedition`** —
   a loss on any floor ends the whole run with no reward for that floor (gear.md section 4), and
   clearing the final floor also ends it (`outcome: "cleared"`); there is no mid-run checkpoint to
   resume a specific floor, matching gear.md's "no checkpoints for restarting at a cleared floor: a new
   run begins at floor 1."
8. **Dungeon floor battles are individually retrievable `BattleReport` rows** (`kind: "dungeon_floor"`/
   `"dungeon_boss"`), reusing the existing `GET /battle-reports/:reportId` rather than adding a new
   report-retrieval endpoint — `DungeonSettleResultDTO.floorResults` carries each floor's `reportId`.
9. **No per-round state-snapshot endpoint was added.** `BattleParticipantsSnapshotDTO.units[*].maxHp`
   (every unit starts at its own max HP) plus a forward replay of `BattleEventDTO[]`'s `hpAfter`/
   `statusApplied`/`statusExpired` already reconstructs the full HP/status timeline, consistent with
   architecture.md's existing note that the UI "initializes HP from this snapshot and applies each
   recorded `hpAfter`." Adding a redundant per-round snapshot would duplicate data already derivable and
   risk desync between the two representations.
10. **Insufficient gold/materials and a full bag without a replacement are `validation`, not a new error
    code** — consistent with the existing precedent (`equipment/unequip`'s `inventory_full` reason), so
    no new `ErrorCode` member was needed for resource-insufficiency cases.

## Unresolved issues / open items (not blockers, listed in the amendment itself)

- Exact `dungeonId` values, per-dungeon floor counts and rosters are M2-31's content decision; this
  contract's `DungeonRun`/settlement shapes do not depend on the specific count.
- The `150 * ownedHeroCount` recruit cost and the craft/reforge gold/material cost tables remain
  placeholders Economy Designer may retune (M2-28) without a contract shape change.
- `apps/web` client code that currently reads `Hero.classId`/`specializationId` or
  `PartyOrder.order` will need updating by M2-26/27 against the renamed/replaced fields — this is
  implementation, not a further contract decision, but is flagged so M2-26 doesn't discover it late.
- This document does not re-specify combat engine mechanics (cooldown enforcement, crit/dodge rolls,
  status stacking) already frozen in `combat.md`/`classes.md`; only the DTOs/persistence/migration layer
  around them.
