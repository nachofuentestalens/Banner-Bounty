## Scope decisions (recorded, not hidden)

The M3.md milestone row for this task reads: "Server migrations/services/
catalogs, timing/retention, pending changes/respec, seasons/brackets and
snapshots; retry/isolation tests." Three scope boundaries follow from that
text plus "No new mechanics" in the owner's instructions, and are recorded
here rather than discovered by a reviewer:

1. **Only expedition (`kind="pve"`) settlement adopts combat v3.** Dungeon,
   arena and boss combat are untouched (`combat2`/legacy content), per
   contracts.md section 4's own preamble ("this section does not touch
   `POST /dungeon/settle`/`/dungeon/stop`"). `/hero/recruit` still only
   accepts the original six classes — expanding it to the new eight-class
   roster would require combat2-consumers (equip, secondary-class, loadout
   validation, effective-stats display) to branch v2/v3 everywhere, which is
   a materially larger, separately-sequenced integration than "server
   migrations/services/catalogs." Existing heroes' `primaryClassId` values
   are already valid `ClassIdV3` values, so the new `raceId`/
   `primarySpecializationId` columns and the `/hero/specialization/primary`
   and respec endpoints work correctly for every hero today; only recruiting
   a Warder/Weaver hero is deferred.
2. **`/dungeon/start` is unchanged** (still only resolves the original
   `DUNGEONS` v2 list). The dungeon catalog (`GET /dungeons`) correctly lists
   `dungeon_cinder_archive` and reports its real server-side lock state
   (reading the new `DungeonClearRecord` fact), but starting/playing it would
   need the same v2→v3 combat migration as recruit — out of this task's
   bounded scope. `DungeonClearRecord` bookkeeping on `/dungeon/settle`
   (idempotent, written on every `outcome="cleared"`) is implemented and
   tested so the catalog's lock state is already correct today and nothing
   needs revisiting when a later task wires the run itself.
3. **Reward-timing implementation choice**: contracts.md section 4's
   pseudocode computes a credited battle's `rewards` at the point
   `creditedAt` is set, without fully specifying whether the reward *amount*
   is fixed at roll time or recomputed at credit time (which can be a later
   `settle()` call than the roll, for a cached pending battle). This
   implementation computes the reward amount at **credit** time, against the
   account's reward-RNG stream and unequipped-item count as they stand when
   crediting actually happens — matching "overflow conversion reflects
   current inventory" and keeping `BattleReport.rewards` genuinely `null`
   until credited (never pre-computed-then-hidden). Combat outcome/events
   are unaffected — they are fixed at roll time regardless, per
   architecture.md's "same instant, deterministic simulation... only when
   its reward is *granted* differs."

Also recorded: `Expedition.cyclesCompleted` keeps its existing column name
for v3 rows (exposed to clients as `creditedBattles.length`/`wins`/`losses`
via the new DTO) rather than an actual `ALTER TABLE RENAME COLUMN`, since the
same column is shared with the still-active legacy algorithm and a rename
would be a larger, purely-cosmetic schema change for no behavioral benefit.

## Changes

**Migration (version 5, idempotent, additive-only):** `server_clock`
(single row, high-water mark), `accounts.nextCompletionSequence`,
`heroes.raceId`/`primarySpecializationId`/`lastRespecAt` (DB-level defaults

`dungeon_clear_records`, `competition_epoch`, `season_entries`,

**New repositories:** `serverClockRepository`, `pendingSkillChangeRepository`,
`settlementAggregateRepository`, `dungeonClearRecordRepository`,
`competitionRepository` (epoch/entries/matches/archives/brackets).

`heroRepository` (race/specialization/respec fields and setters),
`expeditionRepository` (v3 columns + `applySettlementV3`),
`battleReportRepository` (v3 columns, `credit()`, feed/retention queries).

**New services:** `expeditionV3.ts` (the variable-duration settlement walk,
wiring `settlement3`/`loadout3`/`combat3`/`builds3` into real persistence,
eviction/aggregate bookkeeping), `heroLoadoutV3.ts` (`/hero/loadout/queue`
and `/cancel-pending`), `expeditionFeedService.ts` (`GET /expedition/feed`),
`specializationService.ts` (`/hero/specialization/primary`),
`respecService.ts` (preview/confirm primary respec, secondary-switch
preview), `codexService.ts` (`GET /codex`), `dungeonCatalogService.ts`
(`GET /dungeons`), `competitionService.ts` (season enter/withdraw/standings/
matches/account-state, tournament bracket, the shared lazy
`ensureSeasonAdvanced` step). **Amended**: `expeditionService.ts`
(start/settle/stop now dispatch on `rulesVersion` between the untouched
legacy path and the new v3 path), `dungeonService.ts` (`DungeonClearRecord`
write on clear), `heroService.ts` (`/hero/secondary-class` now clears only

reports involving fixture companies — which use Warder/Weaver — render

**Contracts package**: additive `Hero.raceId`/`primarySpecializationId`/
`lastRespecAt` (optional, so `apps/web`'s existing `Hero` literals keep
compiling), new request schemas and response DTOs for every new endpoint

**New endpoints wired in `app.ts`**: `POST /hero/loadout/queue`,

## Unresolved issues / known limitations

- **`migrationProgressionMatrix.test.ts` closes the exit-evidence gap but is
  still bounded**, recorded honestly rather than left unflagged a second
  time: every scenario uses one fixed class (`class_ranger`) and one
  equipped weapon per hero (no armor/trinket, no mixed classes, no gear
  roll near the overflow-conversion boundary, no purchases/crafting in the
  timeline); "stat contribution preservation" is checked against an
  equivalent from-scratch-v5 save, not against a numeric target from
  `economy/m3.md`'s pacing bands; and a legacy *active expedition* carried
  through migration (covered separately by `db/migrations.test.ts`) is not
  combined with the 1/3/5-hero × 30/84/480-minute matrix. If Economy
  Designer's M2-28 pacing-band targets need checking against this
  server-backed path specifically (as opposed to the structural
  fresh-vs-migrated equivalence proven here), that numeric comparison is
  still open. M3-11 should treat this as the server-backed evidence
  `M3-02.md` asked for, not as a substitute for a fresh Economy re-benchmark.
- **Recruit/dungeon-start do not yet accept the 8-class roster or Cinder
  Archive** (scope decisions 1-2 above). A future task should widen
  `/hero/recruit`'s accepted class set and port dungeon run simulation to
  `combat3`/`dungeon3`, coordinated with `equipmentService`/`heroService`'s
  v2-only effective-stats computation so a Warder/Weaver hero behaves
  correctly everywhere, not just in expeditions.
- **Tournament byes are not implemented.** `resolveBracketSeatVacancyV3`
  exists in the pure module but is unused here: normal bracket creation
  always fills all four seats (entries + fixtures), so the recovery-only bye
  path (an operationally-corrupt snapshot) is unreachable in this
  implementation and was left unimplemented rather than built against no
  reachable test case. A future task should wire it before enabling any save
  corruption/recovery tooling that could actually produce a vacant seat.
- **`GET /expedition/feed`'s aggregate-gap-walk** assumes aggregates are
  perfectly contiguous (true under this implementation's single-account,
  single-process eviction, per contracts.md's "always a single contiguous
  range" guarantee) but has not been stress-tested against pathological
  multi-run eviction interleavings beyond the retention/eviction test above.
- **Season/tournament report storage** stores the battle report inline on
  `season_matches.reportJson` rather than in `battle_reports`, since the
  latter has an `accountId` foreign key and season matches have no single
  owning account. This is a deliberate, documented deviation from reusing
  the existing `BattleReportRepository` for this one new case.
- Per-endpoint precondition/apply ordering for `/hero/loadout/queue`
  validates the submitted skill selection *before* running the settlement
  walk (both inside the same transaction), rather than contracts.md's
  literal "walk first, then validate" phrasing — documented in
  `heroLoadoutV3.ts`'s header comment with the reasoning (avoids inventing
  partial-commit-on-reject semantics on top of the existing single-
  transaction mutation framework). Behaviorally equivalent for every case
  this task's tests exercise; a rejected edit simply doesn't also credit
  overdue battles in the same call (the player can resubmit a plain
  `/expedition/settle` first).
- `MAX_BATTLES_PER_SETTLEMENT=500` and `msPerRound=2000` remain the
  provisional values M3-07 already flagged for Economy re-benchmarking once
  real M3 content ships at scale (economy/m3.md section 5); this task did
  not re-run that benchmark against the new server-integrated path.
