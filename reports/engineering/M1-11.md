# M1-11: Implement immutable asynchronous arena battles — evidence report

Date: 2026-10-18 · Owner: Gameplay Programmer

## Result: pass

## Summary

Added `POST /arena/publish`, `GET /arena/snapshots`, `GET /arena/snapshots/:snapshotId`,
`POST /arena/challenge`, and `GET /battle-reports/:reportId` end-to-end against
`design/studio/contracts.md`'s frozen request/response shapes (the Zod schemas for
these endpoints already existed in `packages/contracts`, unused until now). Publishing
copies the account's current party/effective-stats by value into an insert-only
`team_snapshots` row; challenging simulates the challenger's current live party
against a snapshot's frozen data via a new `simulateArenaBattle` engine function and
writes an insert-only `battle_reports` row under the challenger's account only.

`packages/game/src/combat.ts`'s existing `simulateBattle` only models hero-vs-non-hero
content (PvE/boss): the opposing side's AI always targets by lowest party *position*
(combat.md 3.1's enemy-targeting rule) and only heroes get class/specialization
behavior. An arena battle is hero team vs. hero team, so a new `simulateArenaBattle`
function was added (not a modification of the tested PvE path) that applies the
identical class-default/specialization action formulas from combat.md section 3 to
*both* sides, with no new numbers invented. This is a necessary, recorded extension of
combat.md (which does not separately spell out hero-vs-hero combat) — see "Design
decisions" below.

## Acceptance checks

### 1. Two local accounts publish and challenge without the defender being online; only the intended public snapshot fields are exposed — PASS

`apps/server/src/arena.test.ts`, "two accounts publish and challenge without the
defender online...": account B selects its session, calls `/arena/publish` once, then
no B cookie is used again. Account A lists snapshots (`GET /arena/snapshots`, no
cookie), fetches the detail by ID (`GET /arena/snapshots/:id`, no cookie), then calls
`/arena/challenge` with its own session. The summary object asserts exactly the
intended keys (`snapshotId`, `accountId`, `publishedAt`, `rulesVersion`,
`heroClasses`) and explicitly asserts `gold`/`inventory`/`frozenStats` are absent; the
detail response includes `frozenParty`/`frozenStats` but still no `gold`. The returned
report includes `result.outcome` in `{win, loss, draw}`, `kind: "arena"`, a string
`seed`, and `rulesVersion: 1`.

### 2. Changing defender gear/spec later cannot alter a stored snapshot or report; save/restart preserves reports — PASS

`apps/server/src/arena.test.ts`, "changing the defender's gear/spec later...": after
publish + challenge, B's hero row is mutated directly in the DB (`level = 10`,
`specializationId = 'spec_berserker'` — simulating a future equip/level/respec
endpoint, none of which exist yet). The snapshot's `frozenStats` and the full battle
report, re-fetched after the mutation, are asserted `toEqual` their pre-mutation
values. The test then closes the server, reopens the same on-disk SQLite file (not
`:memory:`), rebuilds a fresh `Fastify` instance against it, and re-fetches both the
report and the snapshot detail — both still `toEqual` the originally captured values,
and migrations re-run as a no-op (per the existing migration-reopen test, now
asserting schema version 2).

### 3. Request retries are idempotent; foreign private report retrieval is rejected; opponent live state is never modified — PASS

`apps/server/src/arena.test.ts`, "retries are idempotent, foreign private report
retrieval is rejected...": an identical `/arena/challenge` retry (same `requestId` +
payload) returns a byte-identical response (`toEqual`) via the existing
`runMutation` idempotency-receipt path — no second report row is created (same
`reportId` in both responses). Account B (not the report's owner) fetching the
report by ID gets `404 not_found` (not `403 forbidden`, per contracts.md's
deliberate ID-enumeration-safe decision). A challenge against a nonexistent
snapshotId returns `404 not_found`, as does `GET /arena/snapshots/:id` for an unknown
ID. In the first acceptance test above, B's own `/account/state` revision after A's
challenge is asserted to still equal `1` — exactly what B's own publish call produced,
with no further bump from A's unrelated challenge — confirming the opponent's live
account is never written to.

### 4. Reports include seed/rules/snapshot versions and outcome; timeout is a draw; no arena rewards/ranking are introduced — PASS

Structurally: every report built by `arenaService.challenge` includes `seed`
(string), `rulesVersion` (`CURRENT_RULES_VERSION = 1`), and
`participantsSnapshot.opponent.snapshotId`; `result` is `{ outcome, rounds, finalHp }`
with `outcome` always one of `win`/`loss`/`draw`. No gold/XP/item/claim field exists
anywhere in the arena code path (`arenaService.ts` never imports `rewards.ts`, and
`battle_reports`/`team_snapshots` have no reward columns) — arena is intentionally
reward/ranking-free, matching architecture.md ("M1 arena has no item/currency
rewards, ranking, opponent depletion, or matchmaking").

Timeout-as-draw specifically: `packages/game/src/combat.test.ts`'s new "a stalemate
times out as a draw, not a loss" test drives `simulateArenaBattle` with two
single-combatant teams built so neither can reduce the other to 0 HP within 100
rounds (`maxHp: 10_000`, damage floored to 1/hit via a `def: 100_000` target);
asserts `result.result === "draw"` and `result.rounds === 100`. This exercises the
same step-5 resolution-check code path `simulateBattle` already had covered for
PvE/boss (loss on timeout) — the new test is the arena-specific "draw, not loss"
half of combat.md section 5's timeout rule.

## Design decisions / notable implementation choices

1. **Arena is hero-vs-hero, not hero-vs-generic-enemy.** combat.md's `simulateBattle`
   was written around PvE/boss encounters and has no rule for a hero team facing
   another hero team's specializations (Guardian redirect, Warden healing, etc. for
   both sides). `simulateArenaBattle` reuses every damage/heal/target *formula*
   verbatim from combat.md section 3, generalized to "own team" vs. "opposing team"
   instead of "hero side" vs. "enemy side." No new numbers were invented; this is
   recorded here per `AGENTS.md`'s "make routine reversible decisions... record
   meaningful decisions in the owning document" since combat.md itself doesn't spell
   out two-hero-team combat. A `design/game/combat.md` proposal could formalize this
   explicitly; not filed in this pass to keep scope bounded, but flagged under
   Unresolved issues below.
2. **Arena's cross-team SPD-tie-break (team A before team B)** is this engine's own
   extension of combat.md 2.1's "heroes before enemies" rule, which doesn't apply when
   both sides are heroes. Documented in `arenaSpeedOrderCompare`'s comment; it only
   affects the rare case of an exact SPD tie between a challenger and opponent hero.
3. **Equipment is unconditionally empty for every hero in this build.** M1-10 (item
   instances) has not landed: there is no `item_instances` table and no equip
   endpoint, so `Hero.equipment.*` is always `null` in the current schema. Arena
   effective stats therefore only reflect class/level/specialization until M1-10
   ships; `arenaService.ts`'s `EMPTY_EQUIPMENT` constant documents this inline rather
   than silently assuming equipment bonuses.
4. **Publish/challenge always bump revision (`changed: true`).** contracts.md's
   idempotency protocol conditions the revision bump on "step 5 changed a persisted
   field," and doesn't explicitly classify snapshot/report creation. Since every
   distinct publish/challenge call always creates a brand-new immutable row (unlike
   settlement's zero-credit no-op case), this was treated as always-changed; retries
   of the same `requestId` still correctly return the original stored result/revision
   without a second bump, per the existing `runMutation` harness.
5. **`GET /battle-reports/:reportId`'s response omits `accountId`.** contracts.md's
   `BattleReport` entity has no `accountId` field (ownership is resolved from the
   session, not echoed back); `battleReportService.getOwnedReport` strips it from the
   raw repository row before returning, keeping the challenge-response and
   fetch-by-ID response shapes identical (asserted by `arena.test.ts`'s `toEqual`
   check across a save/reopen cycle).
6. **Snapshot summary shape (`SnapshotSummary`)** is not itself specified byte-for-byte
   in contracts.md beyond "summaries only (no live stats, no inventory)." Chose
   `{ snapshotId, accountId, publishedAt, rulesVersion, heroClasses }` — class IDs
   only, no stats — as a minimal preview; full stats remain available via the by-ID
   detail endpoint for an actual challenge decision.

## Unresolved issues / limitations

1. combat.md does not explicitly cover hero-vs-hero combat; decision 1 above fills
   that gap with the most literal extension of existing formulas. Not filed as a
   `design/game/combat.md` proposal in this pass — flagging it so a future pass (or
   the owner) can decide whether to formalize the "both sides use hero actions
   against each other" rule and the team-A-first tie-break in the frozen document.
2. Equipment bonuses are not yet reachable for arena combat (decision 3) since M1-10
   (item instances/equip endpoints) has not landed; this is expected given M1-11's
   declared prerequisites are only M1-06/M1-07, not M1-10.
3. `node:sqlite`'s experimental status (Node-level, carried forward from M1-07) is an
   ongoing caveat, not new to this task.
4. No hero-creation endpoint exists yet in M1, so the live-server smoke check above
   could only exercise the public health/list endpoints and the validation
   (incomplete-party) path for publish; the full publish/list/challenge/report flow
   is verified by the Vitest integration suite (`arena.test.ts`) against a real
   Fastify + SQLite instance instead, including the save/reopen case across two
   separate `buildServer` instances on the same on-disk file.
