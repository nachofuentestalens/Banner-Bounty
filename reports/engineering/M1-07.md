## What exists (apps/server/src, packages/contracts/src)

- `db/migrations.ts`: versioned, idempotent SQL migrations (`schema_version`,
  `accounts`, `sessions`, `heroes`, `party_orders`, `idempotency_receipts`),
  applied in a transaction, safe to re-run.
- `db/connection.ts`, `db/seed.ts`: opens a `node:sqlite` `DatabaseSync` (file
  or `:memory:`) and seeds two fixed-ID accounts (slots `A`/`B`) via
  `INSERT OR IGNORE`.
- `repositories/*`: `AccountRepository` (revision read/write, slot lookup),
  `SessionRepository`, `HeroRepository` (incl. `ownedBy` ownership check),
  `PartyOrderRepository`, `IdempotencyRepository`.
- `services/sessionService.ts`: select/resolve/logout.
- `services/partyOrderService.ts`, `services/accountStateService.ts`: the one
  mutating endpoint (`PATCH /party/order`) and the one read endpoint
  (`GET /account/state`) implemented end-to-end against the protocol below.
  Expedition/inventory/gold/equipment storage is deliberately out of scope
  (M1-08/M1-10/M1-11 own those tables); `/account/state` returns real
  heroes/partyOrder/revision and M1-01-default placeholder fields for the
  rest, so later tasks extend rather than restructure this shape.
- `mutation.ts`: generic `runMutation` implementing contracts.md's eight-step
  canonical transaction order (idempotency lookup → precondition →
  revision check → apply → conditional revision bump → receipt insert →
  commit), reused by every current and future mutating endpoint.
- `http/cookies.ts`: manual `HttpOnly; SameSite=Strict; Path=/` cookie
  serialization/parsing for the opaque session ID (no third-party cookie
  dependency needed for one value).
- `errors.ts`: `AppError` + `ERROR_STATUS` mapping all seven `ErrorCode`
  values to HTTP status, feeding one Fastify error handler that always
  returns `{ ok: false, error: { code, message, correlationId } }`.
- `config.ts`: loopback-by-default host (`127.0.0.1`), configurable via
  `API_HOST`/`API_PORT`/`DB_PATH`, body limit from `packages/contracts`.
- `packages/contracts/src/index.ts`: full DTO/Zod surface from
  contracts.md — entities, error envelope, bounded-string/array/body
  constants, and request schemas for every endpoint (including ones later
  tasks implement: equip/unequip/specialization/arena), so those tasks reuse
  rather than redefine the contract.

## Acceptance checks

### 1. Fresh database and save reopen/migration pass using isolated fixtures — PASS

`apps/server/src/db/migrations.test.ts`:
- Fresh `:memory:` DB: `currentSchemaVersion` 0 → `runMigrations` → 1.
- Idempotent: running migrations twice leaves exactly one `schema_version` row.
- Reopen: migrations + seed run against a file DB under
  `fs.mkdtempSync(path.join(os.tmpdir(), ...))`, file closed, reopened, migrations
  re-run as a no-op, seeded account ID unchanged. Every fixture here lives
  under the OS temp dir in a per-test subdirectory (cleaned in `afterEach`),
  never under the repo's own `data/` path — test data never touches a real
  save.

Live check (manual, this pass): started the server with no env overrides
(`npx tsx apps/server/src/main.ts` from the repo root) — logged
`[server] listening on http://127.0.0.1:3100`; `GET /health` returned
`{"ok":true,"data":{"status":"ok","schemaVersion":1}}` confirming the
migration ran against the real default `data/banner-and-bounty.sqlite` path
on a cold start. Stopped the process and deleted the generated `data/`
directory afterward (gitignored; confirmed `git status` clean).

### 2. Local account selection/current session/logout; two independent sessions; private cross-account access/mutation rejected — PASS

`apps/server/src/app.test.ts`, `describe("local account sessions")` and
`describe("ownership enforcement across accounts")`:
- `POST /dev/session/select` with slot `A`/`B` returns the matching seeded
  `accountId` and sets `HttpOnly; SameSite=Strict` cookie; unknown slot `C`
  returns `validation`/400.
- Two independently-selected cookies each resolve their own account via
  `GET /dev/session/current`; no cookie → `unauthenticated`/401.
- `POST /dev/session/logout` clears the session; the same cookie no longer
  authenticates afterward.
- A `PATCH /party/order` referencing another account's hero ID is rejected
  `forbidden`/403 without mutating state; the same request with all-owned
  hero IDs succeeds.
- Account B's session reading `/account/state` sees its own (empty) roster,
  never account A's; a cross-account mutation attempt is rejected (400 here,
  since Zod's duplicate-ID check runs before ownership for that particular
  payload shape — the dedicated foreign-ID case above exercises the 403
  path explicitly).

### 3. Same-request retries return stored results; changed-payload reuse and stale revisions fail; concurrent mutations remain atomic — PASS

`apps/server/src/app.test.ts`, `describe("revision and idempotency protocol")`:
- Identical retry (same `requestId` + payload) returns the exact stored
  result, no double-apply (revision stays at 1, not 2).
- Reused `requestId` with a different payload → `conflict`/409, and
  `/account/state` confirms only the first application took effect.
- Stale `expectedRevision` → `conflict`/409 with `details.currentRevision`
  reflecting the true current value.
- Two concurrent distinct requests at the same starting revision via
  `Promise.all`: exactly one commits (200), the other gets `conflict`/409 —
  `node:sqlite`'s single-writer transaction serialization (via `BEGIN
  IMMEDIATE`) makes this race-free, matching contracts.md's A07 guarantee.

### 4. Loopback default, validated payload limits, session cookie handling, consistent API error contract — PASS

- Loopback default: `config.ts` `DEFAULT_HOST = "127.0.0.1"`; confirmed live
  above. `API_HOST`/`API_PORT`/`DB_PATH` env vars override deliberately.
- Payload limits: `app.test.ts` confirms a >16KB body is rejected
  `validation`/400 (Fastify `bodyLimit` wired to `MAX_BODY_BYTES` from
  `packages/contracts`); Zod schemas bound string/array lengths per field.
- Session cookie handling: `HttpOnly`/`SameSite=Strict`/`Path=/` set on
  select, cleared (`Max-Age=0`) on logout; no `Secure` attribute, documented
  as deliberate since the dev server is plain HTTP on loopback.
- Consistent error contract: every error path (Zod validation, `AppError`,
  oversized body, uncaught) funnels through one `setErrorHandler` producing
  `{ ok: false, error: { code, message, correlationId } }`; `app.test.ts`
  asserts this shape explicitly for an `unauthenticated` response.

  session; the live HTTP check was done via PowerShell's `Invoke-WebRequest`
  instead, which worked without issue — not a product defect, just a tooling
  note for future verification passes in this environment.

  intentionally fixed M1-01 defaults, not yet backed by real tables — this is
  in scope for M1-08, not this task; flagged so the next task doesn't assume
  those fields are already persisted.

   contracts.md (equip/unequip/specialization/expedition/boss/arena) reuse

   schemas already in place, but their service logic and backing tables
   (items, expeditions, boss claims, snapshots, battle reports) are M1-08/
   M1-10/M1-11's job, not this task's.

   ongoing caveat to watch across Node version bumps.
3. Live loopback verification in this pass used the default `data/` path
   under the worktree root for a few seconds then deleted it; no persistent
   save file is committed or left behind.
