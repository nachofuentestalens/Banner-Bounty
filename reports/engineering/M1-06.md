# M1-06: Implement deterministic combat and content validation — evidence report

Date: 2026-10-18

Status: **PASS**

## Summary

`packages/content/src` encodes the frozen `content.md` tables (3 classes/6
specs, 9 items, 3 affixes, 3 Old Road enemies, the Tollkeeper boss, 3 starter
heroes) with a self-check (`validateContent()`, run at module load) and
clear-failure lookups (`ContentValidationError` on unknown class/item/affix/
specialization IDs). `packages/game/src` implements pure, seeded combat
(`combat.ts`), effective-stat computation (`stats.ts`), the XP/level curve
(`xp.ts`), reward/drop generation (`rewards.ts`), and a deterministic xorshift32
RNG with exact-rational threshold comparisons (`rng.ts`), per `combat.md` and
`economy/baseline.md`. No clock, storage, network, or browser access anywhere
in either package; `rngSeed`/`RngState` is the only source of variance and is
always caller-supplied.

An earlier run on this task branch produced a report claiming the task was
blocked because prerequisite inputs/design docs didn't exist. That was true at
the time (the repo baseline hadn't landed yet); the baseline, design docs, and
M1-02/M1-04/M1-05 outputs now exist and this report supersedes that one.

## Acceptance checks

- **Same inputs/seed/version yield identical outputs; tests cover targeting
  ties, dead actors, healing/status behavior and 100-round timeout.**
  `combat.test.ts` — "same inputs/seed/version yield identical outputs"
  (direct determinism assertion, `toEqual` on two runs of the same inputs);
  SPD-tie heroes-before-enemies/slot-index tie-break; focus-fire live
  retargeting on a mid-round kill; a one-shot kill removing the target from
  later targeting the same round; Mend's healing-cap clamp (worked example 6);
  100-round timeout as loss (pve/boss) and draw (arena). **PASS.**

- **Three classes and six specs are encoded and each spec has a behavior
  test; invalid content and references fail clearly.**
  `content/index.ts` encodes `class_vanguard`/`class_ranger`/`class_arcanist`
  and all six specialization IDs with class ownership
  (`getSpecializationClass`, `assertSpecializationForClass`).
  `combat.test.ts`'s "one behavior test per specialization" block covers
  Guardian (redirect split), Berserker (HP-threshold damage bonus), Marksman
  (execute-threshold bonus vs. fallback), Pathfinder (+2 SPD without
  overriding its own action), Pyromancer (Burn tick amount), Warden (Mend
  heal amount) — plus a separate boss-pattern test (Toll Strike/Toll Smash).
  `content/index.test.ts`'s "fails clearly on unknown content references"
  asserts `ContentValidationError` with a specific message for unknown
  classId/definitionId/affixId/specializationId; `validateContent()` throws
  on duplicate IDs, wrong slot counts, wrong enemy/hero counts, and
  non-single-stat affixes. **PASS.**

- **Item instance/affix generation and XP helpers match economy tables with
  deterministic rounding and bounded results.**
  `rewards.ts` implements the exact `d0`-`d3` draw order and short-circuit
  behavior from `baseline.md` section 4/8 (d0 always consumed; d1-d3 skipped
  once an earlier branch doesn't need them), the boss's forced-branch
  guaranteed drop, and the 100-item overflow conversion (5/9 gold). `xp.ts`
  implements `xpToNext(level) = 15*level` and the multi-level-up loop with
  XP discarded at the level-10 cap. `rewards.test.ts`/`xp.test.ts` verify
  determinism for a fixed `RngState`, ID validity across a 500-draw seed
  sweep, the always-consumed-d0 rule, overflow conversion amounts, boss
  reward amounts (150 gold/40 XP/guaranteed uncommon item) and its overflow
  variant, and level-up/cap behavior. All arithmetic is integer
  (`Math.floor`), and `rng.ts`'s `belowThreshold` compares against an exact
  `floor(numerator * 2^32 / denominator)` integer threshold rather than a
  float, per `baseline.md`'s "exact rational boundary" note. **PASS.**

- **Logs have structured events and bounded retention; no Date.now,
  database/browser imports or unseeded randomness inside rules.**
  `simulateBattle` returns a structured `BattleEvent[]` (round, type,
  source/target, amount, resulting HP) bounded by the 100-round cap and the
  encounter's fixed actor count — no unbounded accumulation, no external
  logging sink. `grep` across `packages/game/src` and `packages/content/src`
  (excluding tests) found no `Date.now`, `Math.random`, or `new Date(`, and
  no imports outside `@banner-and-bounty/content` and each package's own
  modules (no database/browser/network imports). **PASS.**

## Design decisions / notable implementation choices

- The seeded RNG algorithm (xorshift32) and `RngState`'s representation as an
  opaque unsigned 32-bit integer are this package's own choice —
  `combat.md`/`baseline.md` fix the draw order and probability boundaries but
  not a concrete PRNG. Recorded in `rng.ts`'s header comment so `apps/server`
  (M1-07/M1-08) persists/round-trips the state verbatim rather than
  reinterpreting it.
- Server wiring (`apps/server` consuming `@banner-and-bounty/game`) is out of
  this task's scope per the backlog brief (deliverables are limited to
  `packages/game/src`, `packages/content/src`, this report); that integration
  is M1-07 (saves/sessions) and M1-08 (expedition/gear/offline progression),
  both of which list M1-06 as a prerequisite.
