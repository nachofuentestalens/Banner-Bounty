# M2-08: Accessibility contrast-ratio audit of core screens — evidence report

Date: 2026-10-19 · Owner: Tools Engineer · Task ID 75235d4c-f326-4847-a6e6-b24287271d62

## Scope

Audited the five core browser screens (`apps/web/src/screens/Expedition.tsx`, `Inventory.tsx`,
`Company.tsx`, `Boss.tsx`, `Arena.tsx`) plus the shared chrome every screen renders (`NavBar`,
focus indicator, toasts) for WCAG 2.1 contrast compliance:

- **1.4.3 Contrast (Minimum)**: normal text ≥ 4.5:1 against its background.
- **1.4.11 Non-text Contrast**: UI components / required graphical boundaries ≥ 3:1.

All five screens' colors are driven entirely from CSS custom properties in
`apps/web/src/styles.css` (confirmed: no screen or component file under
`apps/web/src/screens` or `apps/web/src/components` uses inline `style=` color overrides — only
`className`). This made a single token-driven script sufficient to cover every screen instead of
needing a browser/axe-core pass; no new dependency was added.

## Tooling built

`scripts/audit-contrast.mjs` (new, no dependencies):

- Reads the live `--color-*` tokens straight out of `apps/web/src/styles.css`'s `:root` block
  (not a hand-copied duplicate of the values), so the check stays accurate if tokens change later.
- Implements WCAG relative-luminance contrast-ratio math directly (sRGB → linear → luminance →
  ratio), per the W3C formula.
- Defines the actual foreground/background pairs that occur per screen (29 checks), including:
  - Disabled-button text blended through CSS `opacity: 0.55` against the backdrop behind the
    button (opacity blends toward the backdrop, not toward the other layer, so this is computed
    explicitly rather than assumed).
  - The focus ring (`:focus-visible`) against every background it can appear over.
  - Card/table border tokens against the backgrounds they divide.
- Run: `node scripts/audit-contrast.mjs` (human table, exit code 1 if any non-exempt check fails)
  or `node scripts/audit-contrast.mjs --json` for machine-readable output.

## Commands run and results

```
npm ci                              # install deps in this isolated worktree
node scripts/audit-contrast.mjs     # initial pass: 29 checks, 4 failing
```

Initial run surfaced 4 sub-threshold pairs. Investigation of each, with evidence:

1. **`button:disabled` label (Expedition: start/settle; also used by every screen's buttons)** —
   measured 3.10:1 (need 4.5:1). Grepped `apps/web/src/screens/*.tsx` for `disabled` and confirmed
   every one of these buttons renders with the real HTML `disabled` attribute (e.g.
   `Expedition.tsx:140`, `Expedition.tsx:147`). WCAG 2.1's own Understanding doc for 1.4.3 states
   text that is part of an **inactive** UI component is exempt from the contrast requirement.
   **Conclusion: not a compliance defect** — measured and logged as exempt, not silently ignored.
2. **`.spec-picker button:disabled` → `.spec-desc` (Company screen)** — measured 2.98:1 (need
   4.5:1). Same situation: `Company.tsx:65` renders `disabled={pending}` on the real button
   element. **Exempt for the same reason**, measured and logged, not fixed.
3. **`:focus-visible` ring against a brass button's own fill** — initially modeled as a check, but
   removed before the final run: `outline` with the positive `outline-offset` this codebase uses
   (`styles.css` `:focus-visible` rule) paints *outside* the element's border box, so the ring is
   always rendered over the **parent's** background (screen/panel/panel-raised), never over the
   button's own fill. Checking it against brass was a modeling error, not a real rendering path;
   corrected rather than reported as a false "fail." The three real backdrops (screen bg, panel
   bg, panel-raised bg) all measured well above 3:1 (10.27 / 9.28 / 8.24).
4. **`--color-border` (shared token: table row dividers, card/panel edges)** — measured 1.79:1 on
   screen bg (need 3:1). This is a genuine defect: these borders are the only divider shown
   between combat-log/compare-table rows and distinguish panel/card edges from the background, so
   they count as required UI-component boundaries, not purely decorative. **Fixed** (see below).

### Fix applied

`apps/web/src/styles.css`: `--color-border: #4a4337` → `#7a715a` (a lighter shade of the same
warm-neutral family already used — no new hue introduced, stays inside the "warm charcoal ...
muted brass" direction in `design/game/interface.md`). Chosen specifically because it clears 3:1
against both contexts the token is used in against dark surfaces (screen bg and panel bg), without
touching the brass/teal/red tokens.

I considered and rejected scoping a brand-new border token instead of adjusting the shared one:
the only place `--color-border` sits against a *light* background is the base `button` rule's
border against its own brass fill, and a button remains identifiable by its brass fill color
alone (the border there is reinforcement, not the sole boundary cue), so reusing the single
token was the smaller, reversible, no-new-decision change.

Re-ran after the fix:

```
node scripts/audit-contrast.mjs
```

```
29 checks, 0 failing, 2 exempt (measured but below threshold on inactive controls).
```

(The table border check that failed before now measures 3.62:1 on screen bg, 3.27:1 on panel bg,
both re-added in the script as named cases — this is the same script, same run, not a new
fixture.)

## What was fixed vs. logged

- **Fixed**: `--color-border` token (1.79:1 → 3.62:1 on screen bg; 1.62:1 → 3.27:1 on panel bg),
  verified by re-running the same script after the change.
- **Not fixed, not a defect**: disabled-button/disabled-`.spec-desc` text ratios (3.10:1, 2.98:1).
  Confirmed via WCAG 1.4.3's own exemption for inactive controls and via code inspection that
  these buttons use the real `disabled` attribute. No P2 — this is expected, documented behavior,
  not an open issue.
- **No P2 logged this task.** The one real failure found had a direct, in-palette fix; nothing
  required a new visual/art-direction decision.

## Unresolved issues

None outstanding from this audit. If the owner later wants disabled controls to read more clearly
despite the WCAG exemption (a product/UX call, not a compliance gap), that would need an explicit
decision on a new disabled-state treatment — not something to change unilaterally here.
