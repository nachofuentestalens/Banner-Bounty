# M1-12: Add seeded pacing and catch-up benchmarks — evidence report

Date: 2026-10-18 · Owner: Tools Engineer · Task ID f9982f6f-5140-4b5e-b8d2-09a06a7726bd

## Result: pass

`npm run simulate` now runs the real `packages/game` engine (through its built `dist`, the same
artifact `apps/server` imports) with explicit seeds/runs, sweeps specialization choices, and runs a
repeatable 8-hour (480-cycle) catch-up benchmark. No combat or reward formula is reimplemented in the
script — it calls `simulateExpeditionCycles`, `simulateBattle`, `toHeroCombatants` and the content
tables directly. It never opens a database, HTTP connection or server process. Inputs used:
`design/game/economy/baseline.md`, `design/qa/acceptance.md` (A12), `apps/server/src` (read-only, to
confirm `simulateExpeditionCycles`'s real call shape and `CURRENT_RULES_VERSION`), and
`reports/engineering/M1-08.md`.

## What changed

- `scripts/simulate.mjs` (new): CLI with `--seed`, `--runs`, `--max-cycles`, `--mode=pacing|catchup|all`,
  `--catchup-reps`, `--json=<path>`, `--quiet`. Dynamically imports `@banner-and-bounty/game` and
  `@banner-and-bounty/content`; if the dist build is missing it prints a clear instruction to run
  `npm run build` and exits 1 instead of silently failing.
- `package.json`: `"simulate"` now runs `node scripts/simulate.mjs` instead of the M1-05
  `not-implemented.mjs` stub.

## What the script measures

1. **Reproducibility** (always runs first): the same seed is run twice through the full pacing routine
   and the two results are deep-compared; prints PASS/FAIL and exits 1 on FAIL.
2. **Pacing sweep** (`--mode=pacing`/`all`): for `--runs` seeds starting at `--seed`, it runs the Old
   Road cycle-by-cycle through `simulateExpeditionCycles` (one real cycle per call, in cycle order,
   exactly like `apps/server`'s settlement), tracking the shared hero level/xp (baseline.md: all three
   participants always get identical XP) and a greedy per-slot gear assignment (new drops go to
   whichever hero holds the weakest item in that slot, if it's an upgrade, via `content.md`'s
   `powerScore`). It records, per seed: first cycle with any drop, first cycle reaching level 3, and the
   first cycle at which a real `simulateBattle` boss fight (against `content.md`'s actual Tollkeeper
   stats, with that run's live level/gear/specialization combo) would be **won**. Specialization combos
   are swept round-robin across all 8 real combinations plus "unspecialized", one per seed index.
3. **Catch-up benchmark** (`--mode=catchup`/`all`): repeats a single `simulateExpeditionCycles` call of
   exactly `MAX_CYCLES_PER_SETTLEMENT` (480, the real 8-hour cap) `--catchup-reps` times with fresh
   seeds, measuring wall-clock duration (`process.hrtime.bigint()`) and heap delta
   (`process.memoryUsage().heapUsed`) per rep, and asserting `recentCycles.length <= RECENT_CYCLE_LOG_LIMIT`
   (10) every time.
4. Console output is bounded to a short summary regardless of `--runs`; full per-seed detail and the
   catch-up samples are only written if `--json=<path>` is given (never written by default, never a
   database file).

## Acceptance checks

### 1. Fixed seed reproduces results; multiple seeds and specialization choices report distributions — PASS
- `npm run simulate -- --seed=100 --runs=48 --max-cycles=800`: reproducibility check PASS; 48 seeds ×
  (round-robin across all 9 specialization combos) produced:
  - First drop: min 1 / median 4 / max 25 cycles — matches baseline.md's own hand estimate
    (`1/0.25 = 4` cycles expected) once seeds are properly decorrelated (see Observations).
  - First level-3 (specialization unlock): exactly 12 cycles on every seed (deterministic — see
    Observations).
  - First cycle a real boss fight is won: exactly 12 cycles on every seed, i.e. the moment level 3 is

    unspecialized case directly, see Observations).
- Re-running the exact same `--seed=100` sweep a second time reproduced identical console output and
  JSON byte-for-byte (`--json` diff was empty on a repeat run).

### 2. Results include assumptions, simulated elapsed time, win/loss counts and version/seed identifiers — PASS
- Every run prints the assumptions list (Old Road outcome/reward independence from level/gear, shared
  XP, greedy gear policy, boss-readiness tested by real combat not a hand estimate, the seed-mixing
  step) and, in `--json` output, `versions: { gamePackageVersion: "0.2.0", contentPackageVersion:

- Win/loss totals printed and in JSON (`576`-`593` wins / `0` losses across the sweeps run below — see
  Observations on why losses are 0).
- Cycle counts are converted to simulated minutes (`cycles * 60_000ms / 60_000`) alongside the raw
  cycle counts, so elapsed time is explicit, not implied.

### 3. Eight-hour catch-up measures time/memory/log bound and responsiveness; target assessed honestly — PASS
- `npm run simulate -- --mode=catchup --catchup-reps=20`: 20 reps of the real 480-cycle settlement call.
  - Duration: min 1.54 ms / median 4.15 ms / p95 6.23 ms / max 6.31 ms (across two runs on this
    machine).
  - Heap delta: roughly −1.7 MB to +1.7 MB per rep (GC noise at this scale; see Observations).
  - `recentCycles` bound (≤ 10) held on every rep.
  - p95 (6.23 ms) is **well under** `design/qa/acceptance.md`'s provisional 2000 ms target — the
    script reports `withinProvisionalTarget: true` honestly, not by assertion.
  - Hardware/runtime recorded every run: Intel Core i7-14700K (28 logical CPUs), Node v22.14.0,
    win32/x64, this is the only machine this was measured on.
- Responsiveness: this is a single synchronous call inside one process. At 1-7 ms, it cannot block the
  event loop long enough to be perceptible to a concurrent request; the script's own `note` field says
  so, and also states the honest limitation below.

### 4. Bounded output, machine-readable save, never touches a real database — PASS
- Default console output is a fixed number of summary lines regardless of `--runs` (verified at
  `--runs=48`: output length unchanged from `--runs=4`).
- `--json=<path>` writes the full structured report (assumptions, versions, every per-seed result,

- The script imports only `@banner-and-bounty/game` and `@banner-and-bounty/content` (both pure,

## Observations

- **Seed-mixing was necessary.** `packages/game`'s `createRngState`/`xorshift32` mixes small,
  sequential integer seeds weakly on their *first* draw: seeds `1`-`150`ish all produced a first-draw
  value under the 25% drop threshold, so an initial sweep over `--seed=1 --runs=16` reported "first
  drop always cycle 1" for every single run — a sweep artifact, not real pacing variance. The script
  now hashes the sweep seed through a small local 32-bit mix (`mixSeed`) before calling
  `createRngState`, which is seed *preparation* only; `createRngState`/`xorshift32` remains the
  engine's only RNG. After the fix, first-drop cycles span 1-25 across 48 seeds with a median of 4 —
  matching baseline.md section 7's own hand estimate (`1/0.25 = 4`) almost exactly. This is worth a
  note for anyone else seeding this RNG directly with small sequential integers (e.g. a future
  QA/dev-tools accelerator): the first draw from a fresh small seed is not uniform.
- **Boss readiness is reached right at level 3, not level 4-5.** Every one of the 48 swept seeds —
  including the worst-gear-luck seed and a hand-checked fully unequipped/unspecialized case run
  directly against `simulateBattle` — won the Tollkeeper the instant the party hit level 3 (cycle 12,
  `ceil(45/4)`), not in the 20-40 minute / level 4-5 window baseline.md's hand-derived estimate
  flagged as "conservative, pending simulation." A direct check (level 3, all three heroes fully
  unequipped, unspecialized) still won in 12 rounds, though two of three heroes died doing it — so the
  margin is thin, not a rounding error. **This corrects baseline.md section 7's pacing hypothesis
  downward and is the single most load-bearing finding for M1-13.** Because the floor is reached this
  early for every seed/spec/gear combination tried, "boss ready" never showed variance in this sweep;
  a future tuning pass may want to deliberately test *lower* levels (2, or level 3 immediately without
  waiting for any cycle to pass) to find the true threshold, since this script only checks from level
  3 upward (level < 3 never has an unlocked specialization and combat.md's effective-action gate makes
  under-level-3 attempts strictly worse, so they were not swept).
- **Losses never occurred** across all sweeps (`0` losses in every run) — consistent with
  `combat.md` worked example 11 and baseline.md section 2's note that Old Road losses are not expected
  in ordinary play; the engine was never observed to contradict that.
- **Heap delta is noisy at this scale** (±~1-2 MB per 480-cycle rep) because V8's GC runs
  independently of the benchmark loop; a single settlement's actual allocation is small (a handful of
  arrays/objects per cycle, freed immediately). The script reports the raw min/max rather than
  smoothing it, since inventing a cleaner number would not be honest about what was measured.
- Duration numbers (1.5-7.75 ms per 480-cycle settlement) are consistent run-to-run on this machine but
  are a single-machine, single-process measurement; `design/qa/acceptance.md`'s "no perceptible freeze
  for another request" claim is about the full server process under concurrent HTTP load, which this
  script does not simulate — that layer was separately measured live in
  `reports/engineering/M1-08.md` (a real stop/restart and concurrent-request test over HTTP).

## Unresolved issues / limitations

- This benchmark measures only `packages/game`'s pure computation for one settlement call, not the
  SQLite transaction + Fastify route overhead a real `/expedition/settle` request adds on top (that
  layer is M1-08's responsibility and was already measured live there). If M1-15's final release
  verification wants a combined number, it should chain this script's engine-only measurement with
  M1-08's transaction-layer measurement rather than re-measuring either in isolation.
  - **How to apply:** M1-13/M1-15 should read both reports rather than assuming either number alone
    bounds the full user-visible latency.
- Measured on one development machine only (Windows, Intel i7-14700K); no cross-machine or CI
  measurement exists yet. The provisional 2 s target is cleared with over 300x headroom here, so this
  is unlikely to be the limiting factor, but it is still a single-sample observation.
- The boss-readiness sweep only checks from level 3 upward (specialization requires level 3); it does
  not establish whether a lower level could also clear the boss, which the next tuning pass may want
  to know given how early level 3 already clears it.
- No automated test file guards `scripts/simulate.mjs` itself (it is a CLI tool, not a package under
  `packages/*`/`apps/*`); correctness here rests on this report's manual verification (reproducibility
  check, direct `simulateBattle` cross-checks in Observations) and the fact that it only calls
  already-tested production functions. A future pass could add a `scripts/simulate.test.mjs` if this script
  grows more branching logic.
