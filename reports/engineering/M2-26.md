## Scope and a bounded decision on `apps/server`

The task brief is "implement the M2 rules in `packages/game` and `packages/content` (and the save
migration in `apps/server` if the contracts require it)." The M2 task graph (`design/studio/milestones/M2.md`)
separately assigns M2-27 ("Gameplay Programmer / Tools Engineer: server and browser implementation,
including the full battle view") to wire real endpoints and the DB schema to these new rules.

**Decision:** I implemented `packages/game`/`packages/content` fully and did **not** touch
`apps/server`. Reasoning: `packages/game` is pure (architecture.md: "`apps/server` is the only
package touching `node:sqlite`/clock/RNG") and needs no database migration to exist, build, or be
unit-tested — every function here takes plain inputs and returns plain outputs. Actually cutting the
DB over (dropping `Hero.specializationId`/`PartyOrder`, adding `PartyFormation`/`MaterialBalance`/
`DungeonRun`, rewriting every repository/service/route that reads the old columns, and keeping M1's
existing endpoints/e2e suite green throughout) is a large, inherently server-side change that M2-25's
own "Open items for downstream tasks" section already assigns to M2-26/27 jointly for the
*transaction/RNG-ordering* logic (which I did implement, in `packages/game`) while the schema/route
cutover itself is M2-27's "server implementation" scope. Doing a partial, premature DB rename here
without the matching route rewrite would either break the currently-green M1 endpoints/e2e suite or
require redoing M2-27's job inside this task. I recorded this as the scope boundary; M2-27 implements
the migration + endpoints against the engine functions below.

### Assumptions / decisions recorded (AGENTS.md rule 4)

1. A dual-class hero's Basic Attack is always its **primary** class's basic skill — nothing in
   classes.md specifies which of two classes' basics a dual-classed hero uses, and a hero has exactly
   one "default" action historically (M1 precedent).
2. Combat's `rngSeed` (crit/dodge stream) and the reward RNG stream are independent, per gear.md
   section 1 ("Combat RNG and reward RNG are separate streams"). For a dungeon's multiple floors, each
   floor's combat seed is derived from the run's single persisted seed + floor number
   (`combatSeedForFloor`, documented in `dungeon.ts`) rather than requiring a second persisted/chained
   RNG field — contracts.md's `DungeonRun` only has one `rngState` (the reward stream, matching
   `Expedition.rngState`'s existing M1 purpose) and leaves per-floor combat seeding to this package.
3. A damaging hit's attached status effect (Shield Bash's Weaken, Firebolt/Meteor/Hexblade-Backstab's
   Burn) applies only if the hit is not dodged — generalizing Hexblade's explicit "(not on dodge)"
   wording to every damage+status skill, since a dodged hit "deals 0 damage" and a status riding on a
   missed hit has no documented precedent either way.
4. `combat.md` 8.5's reference LCG is explicitly a substitute-permitted formula ("any deterministic
   PRNG satisfying this seeding/update contract is an acceptable substitute... this is the formula used
   for this document's worked examples"); I reused the engine's existing tested xorshift32
   (`drawUint32`) mod 100, not a second PRNG implementation, since only draw *order* is binding.
5. `boss_<id>`/`enemy_<id>` naming convention (`enemyId.startsWith("boss_")`) is used by
   `encounters2.ts` to flag the Tollkeeper/Drowned Warden as bosses — both existing and new content IDs
   already follow this convention; no new content field was needed.

## Unresolved issues / open items (not blockers)

- **`apps/server` migration/endpoints are fully deferred to M2-27**, per the scope decision above.
  `packages/game`/`packages/content` are ready for M2-27 to wire: `simulateBattleV2`,
  `simulateDungeonFloorBatch`, `resolveCraft`/`resolveReforge`, `resolveAreaOrDungeonReward`/
  `resolveStandaloneBossReward`, and `toHeroCombatantsV2`/`buildEnemyCombatants` cover every new
  endpoint contracts.md's M2-25 addition specifies (`/hero/recruit`, `/hero/secondary-class`,
  `/hero/loadout`, `/party/formation`, `/craft`, `/reforge`, `/dungeon/start|settle|stop`), but none of
  those endpoints or the DB schema exist yet.
- The exact combat-RNG-seed-per-floor derivation (assumption 2 above) is this package's own
  implementation decision, not a contracts.md-fixed field; M2-27 should treat `combatSeedBase` as an
  opaque number it can derive however `/dungeon/start`'s existing `seed(accountId, dungeonId,
  startedAt)` already does, not a new persisted field.
- `reward_area_3` and `dungeon_2_*` reward profiles exist in `packages/content` (gear.md's full table)
  but are unbound to any area/dungeon, per gear.md's own "an unused profile does not require another
  area" — available for a future task without further content/engine change.
- Did not attempt arena-mode v2 in `scripts/simulate.mjs` (the engine supports it — `combat2.test.ts`'s
  timeout test exercises arena mode directly) since no arena-snapshot plumbing exists yet without
  `apps/server`.
