## What changed

**packages/game** (pure; no clock, DB or unseeded RNG)
- `expedition.ts` (new):
  - `computeSettlementWindow(checkpointMs, nowMs)` implements the contracts.md offline algorithm: clamp negative elapsed time, 8 h cap, 480-cycle batch, whole 60 s cycles.
  - `simulateExpeditionCycles` runs N Old Road battles in cycle order against the frozen party. Each win grants 4 XP to each participant, 10 gold and a drop roll (d0–d3 from the persisted `rngState`), and the overflow check runs against the running unequipped count. A loss consumes the cycle with no reward and no RNG draw. The function returns totals plus a bounded log of the 10 most recent cycles.
  - `toHeroCombatants` and `oldRoadEnemyCombatants` are shared helpers.
- `rewards.ts`: `INVENTORY_CAP` is now exported, and the cycle and boss reward results now report `overflowConverted` (the roll that became gold). Existing behavior is unchanged.

**packages/contracts**
- New response DTOs: `ExpeditionViewDTO`, `SettlementResultDTO`, `CycleLogEntryDTO`, `BossChallengeResultDTO`, `FrozenPartyMemberDTO`. Request schemas already existed from M1-07 and are reused as-is.

**apps/server**
- Migration 3:
  - `accounts.gold` (≥ 0) and a new `item_instances` table (`seq` gives a stable inventory order; `equippedBy` mirrors `heroes.equipment*` and is written in the same transaction).
  - New `expeditions` table: status, startedAt, checkpointAt, subCycleRemainderMs, frozenLoadout, rulesVersion, seed, rngState, cyclesCompleted, wins, losses.
  - New `boss_claims` table.
- `runMigrations(db, upToVersion?)` takes an optional cap so a test can build a v2 save and then upgrade it.
- Seed: each dev account gets the three starter heroes (fixed IDs, one per class) and a default party order, idempotently (first-playable.md: "three starter heroes… available immediately"). Before this, a fresh account had no heroes and could not play.
- Repositories: `itemRepository`, `expeditionRepository`, `bossClaimRepository` (new). The hero, account and party repositories gained `findById`, slot/spec/level writes, `getGold`/`addGold` and `insertIfMissing`.
- Services, all through the existing 8-step `runMutation`:
  - `equipmentService` (equip, unequip, specialization).
  - `expeditionService` (start, settle, stop).
  - `bossService` (challenge).
  - `partyLoadout`: shared live-party loading, gear resolution and `grantRewards`.
- Routes: `POST /equipment/equip`, `/equipment/unequip`, `/hero/specialization`, `/expedition/start`, `/expedition/settle`, `/expedition/stop`, `/boss/challenge`.
- `GET /account/state` returns real inventory, gold, expedition (`status`, `checkpointAt`, `frozenLoadout`, `cyclesCompletedSinceStart`, plus `startedAt`/`rulesVersion`/`wins`/`losses`) and `bossClaims` in place of the M1-01 placeholders. It stays read-only.
- `arenaService.ts` (M1-11 code): now uses the shared `loadLiveParty`/`toFrozenMembers`, so published and challenging arena stats include equipped items. Its old comment said gear was "always empty until M1-10"; that limitation no longer applies.

## Decisions made within scope (recorded for the contract owner)

1. **Cap discard advances the checkpoint.** On the formula line, `checkpointAt_new = checkpointAt + credited·60s`, a 10 h absence would leave the checkpoint at T0+8h, and the next settle would credit the "discarded" 2 h. That contradicts worked examples 5 and 6 and the comment "permanently discarded". The implementation therefore uses `checkpointAt + discardedMs + credited·60s`. This reduces to the formula line whenever nothing is discarded, so the 61 s remainder case is unchanged.
2. **Mid-expedition stat timing (open item in contracts.md):** level and XP change live during a run, but combat uses the levels frozen at `/expedition/start`, as the start transaction says ("freezes … hero levels/specs/equipment at start"). New levels affect the next expedition and boss/arena fights immediately, not the current expedition. This also keeps partitioned settlement identical to continuous settlement.
3. **Additive response fields:**
   - settle/stop add `outcomes {wins, losses}`, `overflow {convertedCount, convertedGold}` and `recentCycles` (≤ 10). ui-spec.md needs the overflow fields to show `inventory.overflow`.
   - boss adds `reward` (null when nothing was granted).
   - The start/stop `expedition` view omits `rngState` and `seed`, so a client cannot predict drops.
4. **Unequip at a full inventory** (100 unequipped) returns `validation` with `reason: "inventory_full"`. The 100 cap stays an inventory invariant and unequip cannot create a 101st item.
5. **Error codes and precondition order:**
   - equip/unequip: unknown hero/item → `not_found`, foreign → `forbidden`.
   - specialization: unknown or foreign hero → `forbidden`. contracts.md lists no `not_found` for this endpoint, so it matches party/order.
   - Order: ownership → `active_expedition` → validation (wrong slot / level / class) → `conflict` (item equipped by another hero). All of these run at protocol step 3, so none writes a receipt.
6. **Settlement concurrency:**
   - The bounded simulation (≤ 480 battles) runs before `BEGIN IMMEDIATE`.
   - Inside the transaction, the plan is applied only if the account revision still equals the revision it was planned at; otherwise it is recomputed under the lock.
   - Rewards, item rows, hero XP, the checkpoint/rngState, the revision bump and the receipt commit in one transaction.
7. **Boss seed** = `sha256("boss:accountId:bossId:requestId")`. Combat ignores it (combat.md §7); only the guaranteed drop consumes it. The claim uses a single `INSERT … ON CONFLICT DO UPDATE … WHERE claimedAt IS NULL` inside the challenge transaction, before the report insert.

## Acceptance checks

### 1. 59/60/61 s, partitioned, negative elapsed, 8-hour cap and repeated-cap fixtures match the contract; downtime/reopen preserves state/seed/remainder — PASS
- `packages/game/src/expedition.test.ts`: contracts.md worked examples 1–7 on the pure window function. Also covers exactly 8 h (480 cycles, 0 discarded) and the 20 h absence (480, not 960).
- `apps/server/src/progression.test.ts` "offline settlement timing (A06)", over HTTP:
  - **59 s:** credits 0, revision unchanged, and a retry returns the identical receipt.
  - **60 s:** credits 1, checkpoint T0+60 s, every hero has XP 4.
  - **61 s:** credits 1. Settling at 119 s credits 0 and at 120 s credits 1, so the 1 s remainder was kept.
  - **Partitioned:** settles at 60 s, 125 s, 17m05s and 41m30s give gold, levels/XP, item sequence (definition + affix), checkpoint and cycle count deep-equal to one settle at 41m30s (41 cycles).
  - **Negative elapsed:** a −5 min clock credits 0 with no revision bump; 2 min later it credits 2.
  - **10 h:** credits 480, elapsed 36,000,000 ms, discarded 7,200,000 ms, checkpoint T0+10h. An immediate re-settle credits 0 and gold is unchanged. Heroes cap at level 10 with 0 XP.
  - **Reads:** `GET /account/state` after 3 h is unchanged (revision, gold, checkpoint).
- "downtime, reopen and rules version (A08)":
  - **Restart:** a temp-file save settled at 90 s (checkpoint 60 s, 30 s remainder) is closed and reopened by a new server instance. `/account/state` and the `rngState`/`seed`/`checkpointAt` row are identical after reopen. Catch-up at 41m30s credits 40 cycles, and the totals equal an uninterrupted run.
  - **Rules version:** setting `rulesVersion = 999` makes settle and stop return 400 `validation` `reason: unsupported_rules_version`, and state is unchanged.
- `db/migrations.test.ts`: a v2 save with revision 7 and a level-4 hero upgrades to v3 with revision, hero and `gold = 0` intact.
- Live check (see commands): the real server was stopped for 65 s and a new process was started on the same file. State was identical, and the next settle credited 1 cycle (elapsed 65,730 ms, 10 gold, 4 XP).

### 2. Repeated and concurrent settlement cannot duplicate rewards; inventory and checkpoint commit together — PASS
- **Retry:** reusing the same requestId 15 min later returns the stored body; gold and revision are unchanged.
- **Concurrent requests:** two settles at the same revision, run with `Promise.all`, give exactly one 200 and one 409. Gold, inventory and cycles equal the winner's single grant.
- **Two processes:** two server instances (separate `DatabaseSync` connections) on one save file give 200 and 409 with `currentRevision: 2`, and gold is credited once.
- **Atomicity:** a temp trigger aborts the `item_instances` insert. Settle returns 500 `internal`, and `/account/state` (gold, XP, inventory, checkpoint, revision) deep-equals the pre-call state with no receipt written. After dropping the trigger, the same requestId settles all 60 cycles.

### 3. Party ownership/distinctness, wrong-slot/double equip and active-expedition loadout/spec lock are enforced server-side — PASS
- **Equip and stats:** equipping a Shortsword raises the Vanguard's published arena ATK by exactly 3, and unequipping restores it.
- **Rejected equips** (revision unchanged after all of them):

  | Case | Result |
  | --- | --- |
  | Wrong slot | 400 |
  | Foreign item | 403 |
  | Foreign hero | 403 |
  | Unknown item | 404 |
  | Unknown hero | 404 |
  | Item already on another hero | 409 `conflict` |

- **Swap:** the old item returns to the inventory (`equippedBy` null).
- **Unequip at 100 unequipped items:** 400 `inventory_full`.
- **Specialization:** level < 3 gives `level_too_low`; another class's spec or an unknown spec gives `wrong_specialization`; a foreign hero gives 403; a valid choice persists.
- **Active expedition:**
  - Fresh equip, unequip and spec requests all return 409 `active_expedition`, even with a stale `expectedRevision`.
  - A pre-start equip receipt still replays its original body.
  - Party reorder succeeds and leaves `frozenLoadout` unchanged.
  - A mid-run level-up changes live level (Ranger 1→3) while the frozen level stays 1.
  - Stop at +59 s credits 0, returns status `none` and unlocks specialization.
- **Party:** a missing or incomplete party makes start return 400. Foreign and duplicate party IDs are covered by the M1-07 tests in `app.test.ts` (403, 400). A second start returns 409 `active_expedition`.
- **Stop remainder:** stop at 5m59s credits 5 and discards the 59 s; a restarted run counts from the stop instant.

### 4. Boss first-win reward is atomic and cannot be farmed; overflow conversion is correct; bounded catch-up and logs are implemented — PASS
- **Boss rewards:**
  - A level-1 loss returns a report (retrievable via `GET /battle-reports/:id`) with `rewardGranted: false`; `claimedAt` stays null and gold stays 0.
  - At level 6 the first win grants 150 gold, 40 XP per hero and one affixed item, and sets `claimedAt`.
  - A repeat win returns `rewardGranted: false` and `reward: null`, with no change to gold, items or XP.
- **Boss concurrency:** three concurrent winning challenges give 200/409/409. A further challenge still leaves a single grant (gold 150, 1 item).
- **Boss atomicity:** a trigger aborting the report insert rolls back the claim, gold, item and revision; a clean retry then grants.
- **Boss overflow:** at 100 unequipped items the guaranteed drop becomes 9 gold (total 159), XP is still 40 and the inventory stays at 100.
- **Settlement overflow** (same seed for the empty, 99-item and 100-item runs; fixtures are inserted after start):
  - At 100 items, zero items are created and the unequipped count stays 100.
  - `convertedCount` equals the number of drops in the empty run, and `convertedGold` equals Σ(5 common / 9 affixed) of those drops; total gold = empty-run gold + conversion gold.
  - At 99 items, only the first drop is created and the rest convert.
- **Bounded catch-up:** each settlement simulates at most 480 cycles, and each battle is capped at 100 rounds by the engine. Totals cover every cycle, and `recentCycles` keeps at most 10 entries (game test: 480 cycles → 10 entries ending at cycle 485). Expedition `wins`/`losses` totals persist.
- **Boss usage:** the boss is usable during an active expedition and uses live gear.
- **Auth and validation:** all seven new routes return 401 without a session and 400 `validation` for a malformed requestId/revision.

## Observations
- The `code` field printed blank for live steps 5 and 7: the Windows PowerShell 5.1 error-body reader in my
  script returned empty. The HTTP statuses (409 and 401) are correct, and the vitest suite asserts the
  `active_expedition` and `unauthenticated` codes over the same routes.
- Server tests import `@banner-and-bounty/game` through its built `dist`, which `tsc --build` (the
  typecheck step) emits. A change in `packages/game` is therefore only visible to the server tests after
  typecheck or build. `npm run validate` runs them in that order.
- A level-1 party loses the Tollkeeper; a level-6 party wins it. Pacing bands are M1-12/M1-13's job.
- Combat is fully deterministic and the frozen party never changes mid-run, so every cycle in one
  expedition has the same battle outcome. Cycles still simulate individually so the engine stays general;
  480 battles take a few ms in tests. M1-12 should measure real catch-up cost.
