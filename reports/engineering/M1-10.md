# M1-10: Build the playable browser interface — evidence report

Date: 2026-10-18 · Owner: Gameplay Programmer · Task ID 3e346450-4689-4cff-b285-4332775a5620

## Review follow-up (same date, after initial pass)

A code review found that `apps/web` violated `design/studio/architecture.md`'s "apps/web: ... No
client-authoritative loot, XP, time, stats or victory": `stats.ts` imported `@banner-and-bounty/game`'s
`computeHeroEffectiveStats` to display hero HP/ATK/DEF on `Company.tsx`'s `HeroCard` and in `Inventory.tsx`'s
gear-comparison panel, and `Company.tsx` separately imported `xpToNext` (game) and `getClassDefinition`
(content) for the same purpose. This also added undeclared `apps/web → content/game/contracts` edges to
`contracts.md`'s frozen package graph (only `apps/server` is documented as depending on those three), and
`@banner-and-bounty/contracts` itself was an unused dependency.

**Fix applied:**
- Deleted `stats.ts`/`stats.test.ts` entirely; removed all computed HP/ATK/DEF display from `HeroCard` and the
  gear-comparison panel.
- Removed the `xpToNext` import/display from `HeroCard`; it now shows only the server-reported raw `hero.xp`,
  no computed next-level threshold.
- Removed the `getClassDefinition`/`getItemDefinition` imports. The two structural lookups the UI still needs
  (which two specializations belong to a class, which slot an item definition belongs to) are now local literal
  data in the new `apps/web/src/frozenIds.ts`, duplicating only the permanent *IDs* from `design/game/content.md`
  (same category of move as `copy.ts`'s verbatim `copy.md` strings) — no numeric stat/bonus table, no formula,
  nothing computed from mutable hero state.
- Removed `@banner-and-bounty/content`, `@banner-and-bounty/game`, `@banner-and-bounty/contracts` from
  `apps/web/package.json` and re-ran `npm install` (lockfile updated, confirmed no stray transitive edge).
- `Inventory.tsx`'s gear-comparison panel now shows a text-only "Now → After" (item name + description), with
  an explicit inline note that exact stat deltas aren't available until the server exposes computed stats —
  see the `contracts.md` proposal filed alongside this report.
- Re-ran `npm run validate` from the repo root: typecheck clean, 24 files / 208 Vitest tests passing (2 fewer
  than before, from deleting `stats.test.ts`'s 2 tests), production build clean. `apps/web`'s bundle shrank from
  180.96 kB to 175.40 kB, consistent with the removed package imports.

**Root cause, not fully closed by this task:** `ui-spec.md`'s Company/Inventory screens require displaying
computed effective stats, but no `contracts.md` endpoint returns them — `GET /account/state`'s `Hero` shape is
raw `{ level, xp, specializationId, equipment }` only. Per the review's own guidance, the correct fix is
extending the server response (not a client recompute), which is `apps/server` work outside this task's
declared write scope (`apps/web`, `reports/engineering`). A `contracts.md` proposal and a follow-up
`apps/server` task are filed with this report (see the task's final reply) rather than silently re-adding the
client-side computation.

## Result: partial

All six screens (Account Selector, Company, Expedition, Inventory, Boss, Arena) are implemented against the
real server endpoints per `design/game/ui-spec.md`, with no hard-coded success, fake reward, or disconnected
button — every mutating control calls the frozen `design/studio/contracts.md` endpoint with a client-generated
`requestId`/`expectedRevision` and re-renders from the server's response. Typecheck, the full Vitest suite, and
a production build all pass, and the client's request/response shapes were verified against a live server
instance over a full account-A/account-B walkthrough (session select → party → expedition start/settle/stop →
boss challenge → arena publish/list/preview/challenge).

Marked **partial**, not **pass**, because acceptance check 3 (keyboard/focus/viewport/contrast inspection) is
implemented per spec but not interactively confirmed in an actual browser: no browser-automation tool (Chrome
extension, built-in browser, or screenshot capability) was available in this session, and launching one was
outside this task's tool access. This is a limitation to flag for QA/M1-15, not a claimed pass.

## What changed

**apps/web/src** (new unless noted):
- `api.ts` — fetch wrapper: builds mutation payloads with a fresh UUID `requestId`, classifies failures as
  `NetworkError` (transport failure) vs `ApiError` (parsed `ErrorDTO`), per `contracts.md`'s envelope.
- `copy.ts` — every copy.md string used by the UI (classes/specs/items/affixes/area/enemies/boss/onboarding/
  state copy) plus the exact `ui-spec.md` "Copy additions needed" table (nav labels, action labels, disabled-
  state text), implemented verbatim since `design/game/narrative/copy.md` itself is outside this task's write
  scope.
- `types.ts` — view-model types matching the server's actual JSON (verified live, see Acceptance below) rather
  than the raw `packages/contracts` entity types, since `buildAccountState`/service responses compose ad hoc
  shapes not yet promoted to named contract exports.
- `stats.ts` — display-only effective-stat computation, delegating to `@banner-and-bounty/game`'s
  `computeHeroEffectiveStats` (the same pure combat.md formula the server uses) rather than re-deriving it;
  no combat outcome is ever computed client-side.
- `rules.ts` — pure client-side gating helpers (`isPartyComplete`, `isExpeditionActive`,
  `canChooseSpecialization`, `canEditEquipment`) mirroring `ui-spec.md`'s `disabled.*` rules; unit-tested.
  These are UX conveniences only — every one of them is re-checked server-side.
- `useAccountState.ts` — the single `GET /account/state` poll loop (5s interval while mounted), shared by every
  screen so a mutation response and the next poll tick never race into inconsistent local state; owns the toast
  queue and offline flag.
- `runMutation.ts` — shared mutation dispatch: routes `conflict` → refetch, `validation`/`forbidden`/
  `not_found`/`active_expedition` → rejected toast, `internal` → server-error toast (with `correlationId`),
  transport failure → offline toast.
- `components/`: `LoadingPanel`, `Toasts` (`OfflineBanner`/`ToastList` covering rejected/server-error/conflict
  with `role="status"`/`role="alert"` live regions), `NavBar` (five `nav.*` links + logout, real buttons),
  `BattleResultPanel` (shared by Boss/Arena: win/loss/draw branch, round-by-round event table in a labeled
  scrollable region).
- `screens/`: `AccountSelector`, `Company` (hero cards, party reorder via up/down buttons, specialization
  picker gated by level/expedition state), `Expedition` (area summary, start/settle/stop, client-side countdown
  explicitly labeled as a display estimate, settlement result panel with offline-cap/overflow notes and the
  10-entry recent-cycle log), `Inventory` (slot/owner filters, equip/unequip, gear comparison before/after
  table, empty/full-inventory states), `Boss` (reward-state badge, challenge, result panel), `Arena` (publish,
  opponent list, snapshot preview with version/date framing, challenge, win/loss/draw result).
- `styles.css` — interface.md's warm-charcoal/cream/brass/teal tokens, `:focus-visible` rings, a 640px
  breakpoint collapsing every grid to a single column, and a `prefers-reduced-motion` override.
- `App.tsx` (rewritten) — session bootstrap (`GET /dev/session/current` → unauthenticated/offline/authenticated),
  a hand-rolled `currentScreen` switch (no router, per `interface.md`), route-change focus on each screen's
  `<h1>`.
- `App.test.tsx` (rewritten from the M1-05 health-check scaffold), `rules.test.ts`, `copy.test.ts`, `stats.test.ts`
  (new) — see Acceptance below.

**Wiring:**
- `apps/web/package.json` — added `@banner-and-bounty/contracts`/`content`/`game` as dependencies (display-only
  stat/content reuse; no combat/progression logic duplicated).
- `apps/web/vite.config.ts` — proxy extended from `/health` only to every API path group (`/dev`, `/account`,
  `/party`, `/equipment`, `/hero`, `/expedition`, `/boss`, `/arena`, `/battle-reports`).

## Decisions made within scope

1. **View-model types live in `apps/web/src/types.ts`, not imported from `packages/contracts`.** The contracts
   package exports request schemas and a few M1-08 DTOs, but `buildAccountState`/`arenaService`/`bossService`
   return additional ad hoc shapes (e.g. the `/account/state` envelope, `SnapshotSummary`, `ChallengeResult`)
   that were never promoted to named exported types. Reusing them by hand-matching the server's actual JSON
   (verified live, see below) was the bounded option; promoting them to `packages/contracts` would be a
   contract-surface change outside this task's write scope.
2. **No copy.md key exists for a loss/draw battle-result line** (`ui-spec.md` unresolved issue 2, still open).
   `BattleResultPanel` renders the server's structured `report.result.outcome` with a plain "Victory"/
   "Defeated"/"Draw" label rather than inventing narrative copy outside this task's scope.
3. **Gear comparison uses already-fetched state only**, per `ui-spec.md`: the "before/after" table recomputes
   `computeHeroEffectiveStats` locally on a hypothetical loadout; it never calls the server to preview, and the
   actual equip call is a separate explicit confirm step.
4. **Polling interval is 5s** (the exact value `ui-spec.md` leaves to M1-10), matching the example in "Global
   conventions."

## Acceptance checks

### 1. Real persisted state end-to-end; no hard-coded success/fake reward/disconnected button
**Evidence (live server, see "Exact commands run"):** a scripted walkthrough against `npx tsx src/main.ts` on a
real on-disk SQLite file exercised: session select (A), `GET /account/state`, `expedition/start`,
`expedition/settle`, `expedition/stop`, `boss/challenge` (level-1 loss), account B `arena/publish`, public
`GET /arena/snapshots`/`:id`, account A `arena/challenge` (win). Every response's exact JSON shape — field
names, nesting, `result.outcome` values — was confirmed to match what `types.ts`/the screens read (e.g.
`expedition.cyclesCompletedSinceStart`, `settlement.recentCycles`, `report.result.outcome`). No part of the UI
renders a result without first receiving it from one of these calls; every mutating button is wired to a real
`post`/`patch` call with `mutationPayload(revision, …)`. **Result: pass.**

### 2. Required loading/empty/error/reconnect/conflict states; no duplicate-submission context loss
`npm run validate` (typecheck + 210 Vitest tests across 25 files + production build) passes. `App.test.tsx`
covers the loading → unauthenticated → authenticated transitions with a mocked `fetch`. `runMutation.ts`
centralizes the conflict/rejected/server-error/offline dispatch so every screen's mutation handler gets
identical behavior (refetch-then-retry on `conflict`, toast-and-preserve-context otherwise) rather than
reimplementing it per screen. Every mutating button sets a local `pending` flag and disables itself while its
own request is in flight (ui-spec.md: "a UX courtesy, not the correctness mechanism" — the server's idempotency
receipt is what actually prevents a double-apply, exercised by M1-08's retry/concurrency tests). Empty states
(`state_empty_inventory`, `arena_no_opponent`) and the full-inventory note render from the real fetched arrays,
not a flag. **Result: pass** (verified by test + code inspection; the live walkthrough above also exercised the
real conflict path implicitly through `expectedRevision` tracking across calls).

### 3. Keyboard actions/focus, 1280×720/390px layouts, contrast, accessible labels
**Implemented, not interactively verified — partial.** Every interactive element is a real `<button>`/
`<select>`/`<input>`; `:focus-visible` is styled with a 3px ring and never removed without replacement; each
screen moves focus to its `<h1>` (`tabIndex={-1}` + a mount-effect `.focus()`) on route change; toasts and the
combat/cycle logs use `role="status"`/`role="alert"`/`aria-live="polite"` as specified; wide tables sit in
`role="region" aria-label="…" tabIndex={0}` scroll containers; the 640px breakpoint collapses every multi-column
grid (hero cards, expedition columns, arena columns, item grid, account cards) to one column with no
page-level horizontal scroll. Color tokens follow `interface.md`'s palette description (warm charcoal
background, cream text, brass actions, teal/red status colors) chosen for a high foreground/background ratio,
but no automated or manual contrast-checker run, and no real browser was opened to confirm the responsive CSS
renders as intended or to tab through the actual DOM order. **No browser-automation tool (Chrome extension,
built-in browser pane, or screenshot capability) was available in this session** — this check needs a follow-up
pass with that tooling, ideally as part of QA's M1-15 walkthrough which already owns browser-based verification
with screenshots.

### 4. Optional portraits/icons have usable fallbacks; presentation never controls outcomes
No image/icon assets are referenced anywhere in `apps/web/src` — every class/item/enemy is shown as its
copy.md text label, matching `interface.md`'s "Portrait/icon slots use text or initials until optional original
assets exist." All battle/settlement/reward numbers displayed are read directly from server response fields
(`report.result`, `settlement.rewards`, etc.); no client-side combat or reward computation feeds a displayed
outcome — `stats.ts`'s `computeHeroEffectiveStats` use is display-only labeled stats (HP/ATK/DEF on hero cards
and the gear-comparison table), never a win/loss/reward determination. **Result: pass.**

## Unresolved issues / limitations

1. **Acceptance check 3 (keyboard/viewport/contrast) is implemented per `ui-spec.md` but not interactively
   confirmed** — no browser-automation or screenshot tool was available in this session. This should be the
   first thing re-checked before M1 sign-off, ideally by QA's M1-15 pass which already does screenshot-based
   verification at both viewport sizes.
2. **`ui-spec.md` unresolved issue 2 (loss/draw copy)** remains open: `BattleResultPanel` uses plain
   "Defeated"/"Draw" labels since no `copy.md` key exists for either outcome. Not a blocker — the structured
   `report.result.outcome` is sufficient for correctness — but flagged for the Narrative Designer as `ui-spec.md`
   itself notes.
3. **Equip/unequip and the gear-comparison panel were verified against the real endpoint's error path
   (`not_found` on a bogus item ID) but not against a real equipped item**, since the short live fixture run
   (one boss loss, one arena win, both reward-free) produced no inventory drops to equip. The equip/unequip
   request shape and stat-delta math are the same contract M1-08 already tested exhaustively over HTTP
   (wrong-slot/duplicate/foreign-item/active-expedition cases); this task adds the UI wiring on top of that
   already-verified surface, not a new path.
4. **View-model types in `apps/web/src/types.ts` are hand-matched to the server's current JSON** rather than
   imported from `packages/contracts` (see Decision 1); a future contracts-package change to promote these
   shapes to named exports would let `apps/web` import them directly instead of maintaining a parallel
   definition.
