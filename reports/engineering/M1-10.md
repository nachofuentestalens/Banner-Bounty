# M1-10: Build the playable browser interface — evidence report

Date: 2026-10-18 · Owner: Gameplay Programmer · Task ID 3e346450-4689-4cff-b285-4332775a5620

## Result: partial

All six screens (Account Selector, Company, Expedition, Inventory, Boss, Arena) are implemented against the
real server endpoints per `design/game/ui-spec.md`, with no hard-coded success, fake reward, or disconnected
button — every mutating control calls the frozen `design/studio/contracts.md` endpoint with a client-generated
`requestId`/`expectedRevision` and re-renders from the server's response. Typecheck, the full Vitest suite, and
a production build all pass, and the client's request/response shapes were verified against a live server
instance over a full account-A/account-B walkthrough (session select → party → expedition start/settle/stop →
boss challenge → arena publish/list/preview/challenge).

Marked **partial**, not **pass**, for two reasons: acceptance check 3 (keyboard/focus/viewport/contrast
inspection) is implemented per spec but not interactively confirmed in an actual browser (no browser-automation
tool was available in this session — see Unresolved issues), and acceptance check 4's hero-stat display was
revised mid-task after a review finding (see "Revision history" below) and now shows fewer computed numbers
than originally planned, pending a server-side contract extension.

## Revision history

This report was written in two passes on the same date:

1. **Initial pass:** implemented all six screens. `apps/web` computed hero effective stats (HP/ATK/DEF)
   client-side via `@banner-and-bounty/game`'s `computeHeroEffectiveStats`, and imported
   `@banner-and-bounty/content`/`game`/`contracts` as dependencies to do so.
2. **Review correction (same date):** a code review found this violated
   `design/studio/architecture.md`'s "apps/web: ... No client-authoritative loot, XP, time, stats or victory"
   and added undeclared `apps/web → content/game/contracts` package edges (`contracts.md`'s frozen graph
   documents only `apps/server` depending on those three). The fix: deleted the client-side stat computation
   entirely, removed all three package dependencies, and degraded the Company/Inventory screens to show only
   raw server-reported fields (see "What changed" and "Decisions" below, which describe this corrected,
   **current** state — not the superseded initial pass). A `contracts.md` proposal and a follow-up
   `apps/server` task to add a server-computed `effectiveStats` field were filed with the review reply so the
   UI can show real numbers again once that lands; apps/web does not re-add client computation in the
   meantime.

Everything below this point describes the code as it exists now, after the correction.

## What changed

**apps/web/src** (new unless noted):
- `api.ts` — fetch wrapper: builds mutation payloads with a fresh UUID `requestId`, classifies failures as
  `NetworkError` (transport failure) vs `ApiError` (parsed `ErrorDTO`), per `contracts.md`'s envelope.
- `copy.ts` — every copy.md string used by the UI (classes/specs/items/affixes/area/enemies/boss/onboarding/
  state copy) plus the exact `ui-spec.md` "Copy additions needed" table (nav labels, action labels, disabled-
  state text), implemented verbatim since `design/game/narrative/copy.md` itself is outside this task's write
  scope.
- `types.ts` — view-model types matching the server's actual JSON (verified live, see Acceptance below) rather
  than the raw `packages/contracts` entity types, since `buildAccountState`/service responses compose ad hoc
  shapes not yet promoted to named contract exports.
- `frozenIds.ts` — the only static "content" data apps/web holds: which two specializations belong to each
  class, and which equipment slot each item definition belongs to. These are literal IDs duplicated directly
  from `design/game/content.md`'s frozen tables (the same category of move as `copy.ts`'s verbatim `copy.md`
  strings) — no numeric stat/bonus table, no formula, and no package import. This file exists specifically so
  `apps/web` does not need to depend on `@banner-and-bounty/content`.
- `rules.ts` — pure client-side gating helpers (`isPartyComplete`, `isExpeditionActive`,
  `canChooseSpecialization`, `canEditEquipment`) mirroring `ui-spec.md`'s `disabled.*` rules; unit-tested.
  These are UX conveniences only — every one of them is re-checked server-side.
- `useAccountState.ts` — the single `GET /account/state` poll loop (5s interval while mounted), shared by every
  screen so a mutation response and the next poll tick never race into inconsistent local state; owns the toast
  queue and offline flag.
- `runMutation.ts` — shared mutation dispatch: routes `conflict` → refetch, `validation`/`forbidden`/
  `not_found`/`active_expedition` → rejected toast, `internal` → server-error toast (with `correlationId`),
  transport failure → offline toast.
- `components/`: `LoadingPanel`, `Toasts` (`OfflineBanner`/`ToastList` covering rejected/server-error/conflict
  with `role="status"`/`role="alert"` live regions), `NavBar` (five `nav.*` links + logout, real buttons),
  `BattleResultPanel` (shared by Boss/Arena: win/loss/draw branch, round-by-round event table in a labeled
  scrollable region).
- `screens/`: `AccountSelector`, `Company` (hero cards showing class/level/raw XP/specialization/gear names,
  party reorder via up/down buttons, specialization picker gated by level/expedition state — no computed stat
  numbers, see Decision 3), `Expedition` (area summary, start/settle/stop, client-side countdown explicitly
  labeled as a display estimate, settlement result panel with offline-cap/overflow notes and the 10-entry
  recent-cycle log), `Inventory` (slot/owner filters, equip/unequip, a text-only item-name/description
  comparison panel — no computed stat deltas, see Decision 3 — empty/full-inventory states), `Boss`
  (reward-state badge, challenge, result panel), `Arena` (publish, opponent list, snapshot preview with
  version/date framing, challenge, win/loss/draw result).
- `styles.css` — interface.md's warm-charcoal/cream/brass/teal tokens, `:focus-visible` rings, a 640px
  breakpoint collapsing every grid to a single column, and a `prefers-reduced-motion` override.
- `App.tsx` (rewritten) — session bootstrap (`GET /dev/session/current` → unauthenticated/offline/authenticated),
  a hand-rolled `currentScreen` switch (no router, per `interface.md`), route-change focus on each screen's
  `<h1>`.
- `App.test.tsx` (rewritten from the M1-05 health-check scaffold), `rules.test.ts`, `copy.test.ts` — see
  Acceptance below.

**Wiring:**
- `apps/web/package.json` — dependencies are `react`/`react-dom` only. `@banner-and-bounty/content`,
  `@banner-and-bounty/game`, and `@banner-and-bounty/contracts` were added during the initial pass and removed
  during the review correction (see Revision history); `apps/web` depends on none of the three.
- `apps/web/vite.config.ts` — proxy extended from `/health` only to every API path group (`/dev`, `/account`,
  `/party`, `/equipment`, `/hero`, `/expedition`, `/boss`, `/arena`, `/battle-reports`).

## Decisions made within scope

1. **View-model types live in `apps/web/src/types.ts`, not imported from `packages/contracts`.** The contracts
   package exports request schemas and a few M1-08 DTOs, but `buildAccountState`/`arenaService`/`bossService`
   return additional ad hoc shapes (e.g. the `/account/state` envelope, `SnapshotSummary`, `ChallengeResult`)
   that were never promoted to named exported types. Reusing them by hand-matching the server's actual JSON
   (verified live, see below) was the bounded option; promoting them to `packages/contracts` would be a
   contract-surface change outside this task's write scope.
2. **No copy.md key exists for a loss/draw battle-result line** (`ui-spec.md` unresolved issue 2, still open).
   `BattleResultPanel` renders the server's structured `report.result.outcome` with a plain "Victory"/
   "Defeated"/"Draw" label rather than inventing narrative copy outside this task's scope.
3. **Hero/item effective stats are not computed or displayed in apps/web.** `ui-spec.md` asks for computed
   HP/ATK/DEF on Company's hero cards and a before/after numeric comparison on Inventory's equip panel, but
   `GET /account/state`'s `Hero` shape never included computed stats, and architecture.md prohibits apps/web
   from computing them itself. Company shows raw level/XP/class/spec/gear-name fields only; Inventory's
   comparison panel shows item name/description text only, with an inline note that stat deltas aren't
   available yet. See Revision history above and the `contracts.md` proposal/follow-up task filed with the
   review reply for the intended fix (a server-computed `effectiveStats` field).
4. **Polling interval is 5s** (the exact value `ui-spec.md` leaves to M1-10), matching the example in "Global
   conventions."

## Acceptance checks

### 1. Real persisted state end-to-end; no hard-coded success/fake reward/disconnected button
**Evidence (live server, see "Exact commands run"):** a scripted walkthrough against `npx tsx src/main.ts` on a
real on-disk SQLite file exercised: session select (A), `GET /account/state`, `expedition/start`,
`expedition/settle`, `expedition/stop`, `boss/challenge` (level-1 loss), account B `arena/publish`, public
`GET /arena/snapshots`/`:id`, account A `arena/challenge` (win). Every response's exact JSON shape — field
names, nesting, `result.outcome` values — was confirmed to match what `types.ts`/the screens read (e.g.
`expedition.cyclesCompletedSinceStart`, `settlement.recentCycles`, `report.result.outcome`). No part of the UI
renders a result without first receiving it from one of these calls; every mutating button is wired to a real
`post`/`patch` call with `mutationPayload(revision, …)`. **Result: pass.**

### 2. Required loading/empty/error/reconnect/conflict states; no duplicate-submission context loss
`npm run validate` (typecheck + test + production build, run from the repo root) passes; `vitest run` itself
prints "24 files, 208 tests passing", reconfirmed by re-running it for this review (see "Exact commands run"
for the exact repro and root cause — the true number of distinct source test files in the repo is 16; the
other 8 are duplicate executions of compiled `dist/*.test.js` copies from an unrelated pre-existing
`packages/game`/`packages/content` build-config gap, not 208 genuinely distinct test cases). `App.test.tsx`
covers the loading → unauthenticated → authenticated transitions with a mocked `fetch`.
`runMutation.ts` centralizes the conflict/rejected/server-error/offline dispatch so every screen's mutation
handler gets identical behavior (refetch-then-retry on `conflict`, toast-and-preserve-context otherwise) rather
than reimplementing it per screen. Every mutating button sets a local `pending` flag and disables itself while
its own request is in flight (ui-spec.md: "a UX courtesy, not the correctness mechanism" — the server's
idempotency receipt is what actually prevents a double-apply, exercised by M1-08's retry/concurrency tests).
Empty states (`state_empty_inventory`, `arena_no_opponent`) and the full-inventory note render from the real
fetched arrays, not a flag. **Result: pass** (verified by test + code inspection; the live walkthrough above
also exercised the real conflict path implicitly through `expectedRevision` tracking across calls).

### 3. Keyboard actions/focus, 1280×720/390px layouts, contrast, accessible labels
**Implemented, not interactively verified — partial.** Every interactive element is a real `<button>`/
`<select>`/`<input>`; `:focus-visible` is styled with a 3px ring and never removed without replacement; each
screen moves focus to its `<h1>` (`tabIndex={-1}` + a mount-effect `.focus()`) on route change; toasts and the
combat/cycle logs use `role="status"`/`role="alert"`/`aria-live="polite"` as specified; wide tables sit in
`role="region" aria-label="…" tabIndex={0}` scroll containers; the 640px breakpoint collapses every multi-column
grid (hero cards, expedition columns, arena columns, item grid, account cards) to one column with no
page-level horizontal scroll. Color tokens follow `interface.md`'s palette description (warm charcoal
background, cream text, brass actions, teal/red status colors) chosen for a high foreground/background ratio,
but no automated or manual contrast-checker run, and no real browser was opened to confirm the responsive CSS
renders as intended or to tab through the actual DOM order. **No browser-automation tool (Chrome extension,
built-in browser pane, or screenshot capability) was available in this session** — this check needs a follow-up
pass with that tooling, ideally as part of QA's M1-15 walkthrough which already owns browser-based verification
with screenshots.

### 4. Optional portraits/icons have usable fallbacks; presentation never controls outcomes
No image/icon assets are referenced anywhere in `apps/web/src` — every class/item/enemy is shown as its
copy.md text label, matching `interface.md`'s "Portrait/icon slots use text or initials until optional original
assets exist." All battle/settlement/reward numbers displayed are read directly from server response fields
(`report.result`, `settlement.rewards`, etc.); no client-side combat or reward computation feeds a displayed
outcome. Per Decision 3 above, apps/web no longer computes or displays any hero/item stat number at all — the
only numbers shown anywhere in the UI are values the server returned directly. **Result: pass.**

## Unresolved issues / limitations

1. **`npm run validate`'s "24 files / 208 tests" figure is inflated by a pre-existing duplicate-test-execution
   bug in `packages/game`/`packages/content`, not 208 genuinely distinct tests.** The repo has exactly 16 real
   test source files (confirmed by static enumeration); `packages/game/tsconfig.json` and
   `packages/content/tsconfig.json` lack the `"exclude": ["src/**/*.test.ts"]` entry `apps/server/tsconfig.json`
   already has, so the `typecheck` step's `tsc --build` (which runs before `test` in `npm run validate`) emits
   compiled `dist/*.test.js` copies of 8 of those files, and vitest's project config picks up both copies,
   running each twice. See "Exact commands run" for the full repro and the recommended one-line fix (add the
   same exclude to both tsconfig.json files) — outside this task's write scope (apps/web, reports/engineering)
   to apply directly. Does not affect apps/web's own coverage: its 3 files / 11 tests, run standalone, match
   static enumeration exactly and are unaffected by this gap.
2. **Acceptance check 3 (keyboard/viewport/contrast) is implemented per `ui-spec.md` but not interactively
   confirmed** — no browser-automation or screenshot tool was available in this session. This should be the
   first thing re-checked before M1 sign-off, ideally by QA's M1-15 pass which already does screenshot-based
   verification at both viewport sizes.
3. **Hero/item effective stats are not shown anywhere in apps/web** (Decision 3): Company's hero cards and
   Inventory's comparison panel degrade to raw fields and text-only descriptions until a `contracts.md`
   extension adds a server-computed `effectiveStats` field. A proposal and a follow-up `apps/server` task were
   filed to close this; this is the single biggest functional gap versus the original `ui-spec.md` intent.
4. **`ui-spec.md` unresolved issue 2 (loss/draw copy)** remains open: `BattleResultPanel` uses plain
   "Defeated"/"Draw" labels since no `copy.md` key exists for either outcome. Not a blocker — the structured
   `report.result.outcome` is sufficient for correctness — but flagged for the Narrative Designer as `ui-spec.md`
   itself notes.
5. **Equip/unequip was verified against the real endpoint's error path (`not_found` on a bogus item ID) but not
   against a real equipped item**, since the short live fixture run (one boss loss, one arena win, both
   reward-free) produced no inventory drops to equip. The equip/unequip request shape is the same contract
   M1-08 already tested exhaustively over HTTP (wrong-slot/duplicate/foreign-item/active-expedition cases);
   this task adds the UI wiring on top of that already-verified surface, not a new path.
6. **View-model types in `apps/web/src/types.ts` are hand-matched to the server's current JSON** rather than
   imported from `packages/contracts` (see Decision 1); a future contracts-package change to promote these
   shapes to named exports would let `apps/web` import them directly instead of maintaining a parallel
   definition.
