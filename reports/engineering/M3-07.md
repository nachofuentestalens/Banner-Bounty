## Phase 2 changes and decisions (2026-11-07, prior session — unchanged, carried forward)

- **Timing (`settlement3.ts`):** a generic pure `runSettlementWalkV3` implements
  contracts.md section 4's variable-duration settlement walk — elapsed/cap/
  discard math, cached-pending vs. credited battle semantics, the generalized
  no-op rule (a new reveal bumps revision even with nothing credited), and
  resumable multi-call catch-up under `maxBattlesPerSettlement`. It is
  parameterized over a `rollBattle(rngState) -> {roll, nextRngState}` callback
  so the module has no opinion on which content area or reward table a battle
  belongs to; a `beforeRoll(ordinal)` hook fires immediately before every new
  roll, which is where deferred skill changes apply (see next).
- **Deferred loadouts (`loadout3.ts`):** implements contracts.md section 5.
  `computeBoundaryOrdinalV3` is a direct read of `SettlementStateV3.nextOrdinal`
  — that field is already exactly "the next not-yet-rolled ordinal" by
  construction, whether or not a battle is currently cached as pending, so no
  branch was needed to distinguish the two cases contracts.md's prose
  describes. `queuePendingSkillChangeV3` validates against the frozen
  level/class pool via the existing `validateLoadoutV3` and records the
  boundary; `cancelPendingSkillChangeV3` classifies cancel/already-applied/
  not-found without fabricating a cancellation; `applyDuePendingChangesV3` is
  invoked from the walk's `beforeRoll` hook; `discardPendingOnStopV3`
  implements the stop-time discard-only-unconsumed rule.
- **Competition (`competition3.ts`):** season epoch/window arithmetic; the
  four `fixture_m3_01..04` companies built via the existing `autoFillLoadoutV3`
  at level 5 (exact class compositions from m3-systems.md section 8); seat
  filling; the double-round-robin schedule builder (12 matches: 6 pairs ×
  2 legs, pair-lexicographic ordering, A/B swap between legs, pluggable
  deterministic seed function — never `Math.random`); standings ranking
  (points desc, wins desc, entryId asc); tournament bracket seeding (1v4,
  2v3 by ascending entryId); draw/timeout advancement tiebreak (normalized
  HP -> survivor count -> seed number, matching contracts.md section 11
  exactly); and the recovery-only bye/vacancy matrix (one vacant seat -> bye,
  no report/score; two vacant -> no winner; a bye-decided final withholds
  the title).
- **M3 dungeon runner (`dungeon3.ts`):** `simulateDungeonRunV3` is the piece
  `combat3.ts` alone didn't provide — sequential floor 1..N simulation using
  `buildEnemyCombatantsV3`, stopping on the first loss or the boss floor's
  clear, full HP every floor, normalized per-hero HP-ratio output (feeds the
  tournament tiebreak shape and the tactical matrix below). Isolated from the
  legacy `dungeon.ts`/`combat2.ts` pairing, same per-rules-version separation
  `combat3.ts` already established — a future combat fix must be assessed
  against each rules version independently.
- **Tactical measurement (`scripts/simulate-v3-tactical.mjs`):** runs
  economy/m3.md section 6's protocol for pairs (a) no-new-class
  counterexample, (b) Warder-included, (c) Weaver-included (all vs. an
  equal-gear glass-cannon five, against Cinder Archive floors 1-4), and
  (e) the three races (identical level-5 3-hero class spread) against Old
  Road. **Pair (d), the 16 specialization pairs, is not run this phase** —
  completed in phase 3 below.
- **Catch-up benchmark (`scripts/simulate-v3-catchup.mjs`):** benchmarks one
  real `runSettlementWalkV3` call at the full 8-hour cap using actual
  `combat3` battles, 20 repetitions, same min/median/p95/max + hardware
  report shape as the existing legacy `--mode=catchup` benchmark.
- Both package indexes (`packages/game/src/index.ts`) export every new
  module. `package.json` gained `simulate:v3-tactical`/`simulate:v3-catchup`
  script entries alongside the existing `simulate`. No Design/Leadership/QA
  document was edited; `packages/game/M3.md` gained a "Phase 2" section with
  the same content summarized here.

## Phase 3 changes and decisions (2026-11-07, this session)

- **`scripts/simulate-v3-tactical.mjs` extended** (same file, not a rewrite):
  - `hero()` now takes an options object (`raceId`/`secondaryClassId`/
    `primarySpecializationId`/`equipment`) instead of a positional `raceId`
    only, so every pair builder can vary equipment and specialization
    without new per-pair boilerplate. All four existing party builders
    (`glassCannon5`, `noNewClassBalanced5`, `warderIncluded5`,
    `weaverIncluded5`) now take an `equipment` parameter and forward it.
  - Added `EQUAL_UNCOMMON_GEAR`: one uncommon weapon/armor/trinket (one
    affix each, in-range value), **identical on every hero on both sides
    of every pair** — a trivially valid instance of economy/gear.md
    section 2's "equal total gear budget (same rarity distribution and
    affix count)", and the dungeon's actual intended entry condition
    (economy/gear.md section 7: "five level-5 heroes with equal-budget
    uncommon gear"), which the phase-2 run used a no-gear simplification
    for instead. Pairs (a)/(b)/(c) now run **twice**: once with the
    original no-gear equipment (kept for continuity with the phase-2
    report) and once with `EQUAL_UNCOMMON_GEAR`.
  - `runPair` gained a `dungeonId` parameter (was hardcoded to Cinder
    Archive) and now also reports `avgRounds` (summed `battle.rounds`
    across floors), closer to economy/m3.md section 6 item 4's "mean
    rounds-to-clear" metric than the floor-count proxy alone.
  - Added `specializedParty()` + `runSpecializationPairs()` implementing
    **pair (d)**: all 16 entries of the real `SPECIALIZATIONS_V3` table
    (not a hand-copied list), each run as specialized-hero-vs-unmodified-
    twin (only `primarySpecializationId` differs) against
    `dungeon_aqueduct_depths` — economy/m3.md section 6 item 1's "existing
    dungeon" (pre-M3 content, so the new dungeon's own contrast design
    doesn't confound the measurement) — with `EQUAL_UNCOMMON_GEAR` and 32
    paired seeds per specialization, same counterexample-surfacing
    discipline as the other pairs. `autoFillLoadoutV3` at level 5 always
    slots both of a class's two actives (every class has exactly two
    actives total), so the specialization's modified skill is guaranteed
    present without hand-listing skill IDs per pair.
- **`packages/game/src/codex3.ts` (new) + 7 tests**: a pure assembler over
  the already-frozen, already-validated `CLASSES_V3`/`SKILLS_V3`/
  `SPECIALIZATIONS_V3`/`RACES_V3` tables (`validateContentV3` already
  checks the 8/40/16/3 counts and per-class 1-basic/2-active/2-passive/
  2-specialization shape this module relies on). `buildCodexV3()` produces
  m3-systems.md section 6's required shape exactly: all eight classes with
  full levels-1-10 stat curves, all 5 skills per class **including locked
  ones shown with their unlock level** (never hidden, matching section 6's
  explicit instruction), both specializations per class, a named 25%
  secondary-contribution constant, and the three race tradeoffs. It
  deliberately does not re-derive targeting/row/taunt-exception prose or
  specialization effect copy — those stay sourced from m3-systems.md/
  combat.md and design/game/narrative/copy.md (already written by
  Narrative Designer in M3-06) by the UI layer, the same split
  `apps/web/src/skillMechanics.ts`/`copy.ts` already use for M1/M2's Codex
  screen today. Editing that screen or wiring a server catalog endpoint is
  real browser/server work, out of this task's scope (M3-08/M3-09);
  `buildCodexV3()` is the one pure function both tasks can call instead of
  re-deriving this join themselves.
- Both package indexes (`packages/game/src/index.ts`) export
  `codex3.ts`. No content table, combat executor or design/QA document was
  edited — only the tactical script extended and one new pure module
  added. `packages/game/M3.md` gained a "Phase 3" section with the same
  content summarized here.
