# M3 engine integration notes

M3-07, phase 1 (2026-11-07). Implementation is incomplete; see
`reports/engineering/M3-07.md`. Frozen authority remains `design/game/m3-systems.md`
and the M3-05 additions to `design/studio/contracts.md`.

- `packages/content/src/v3` exports explicitly versioned tables and validation.
  `M3_RULES_VERSION = 3` reserves a numeric rules identity for M3. The existing
  server's current version stays unchanged until M3-08 handles migration and routing.
  `msPerRound=2000` and the 500-battle settlement budget remain provisional.
- `combat3.ts` is an isolated executor derived from the baseline `combat2.ts`.
  The legacy executor and its tables stay intact for captured old runs. Shared
  stat/gear/RNG primitives are reused only where their behavior is unchanged.
  Any later shared-primitive change needs legacy replay regression coverage.
  A combat fix must be assessed separately for each supported rules version;
  do not silently apply new balance rules to an old executor.
- M3 builds explicitly require race and nullable primary specialization.
  Validate against the frozen build level and class pool. Recompute stats with
  `computeBattleStartStatsV3` from class curves and equipment every battle;
  never use an earlier effective-stat result as the next baseline. Race, Rooted
  and Thick Hide percentages are summed before rounding.
- Hero and enemy IDs must be distinct across both combat sides. Formation slots
  are authoritative, and the executor normalizes input arrays by slot before
  generating events. Enemy builders preserve gaps rather than compacting slots.
- `status_remove` events carry `statusExpired` for immediate removal (Fortify,
  Haste including Choir dodge, Weaken, replaced Taunt). Replay must process this
  field at the recorded event, separately from the round-end `status_expire`.
  No UI interpretation or live API has been changed in this phase.
- Pure primary-respec/secondary-switch previews preserve unrelated fields and
  never charge resources, read time or change cooldown timestamps. M3-08 owns
  ownership, revision, active-run locks, receipts, funds and atomic persistence.
- `simulateBattleV3` currently returns the existing battle result/event shape.
  M3-08 must also freeze full input race/spec/gear/loadouts in persisted report
  and competition snapshots; summary units alone cannot reconstruct a build.

Next within M3-07: full codex metadata/copy, pure duration/settlement and pending
loadout state, competition schedules/standings/tournament helpers, fixtures,
production simulation matrix, performance evidence and remaining invariant tests.
Server/database/browser integration stays with the existing M3-08/M3-09 tasks.

## Phase 2 (2026-11-07): timing, deferred loadouts, competition, simulation

- `settlement3.ts` implements contracts.md section 4's variable-duration
  settlement walk as a generic pure function (`runSettlementWalkV3`),
  parameterized over a `rollBattle` callback rather than hardcoding one
  reward table or content area — the credited/pending/no-op/boundary
  semantics are the actual persisted contract; which battles get rolled is
  a caller concern (M3-08 wires the real reward RNG stream and persistence).
  All five contracts.md worked examples (W1-W5: connected polling, offline
  batch, retry-is-pure, 8h-cap resumable catch-up, clock-rollback no-op) are
  reproduced as tests against synthetic deterministic battle sequences.
- `loadout3.ts` implements contracts.md section 5's deferred skill-change
  protocol: queueing computes `boundaryOrdinal` as a direct read of
  `SettlementStateV3.nextOrdinal` (that field already *is* "the next
  not-yet-rolled ordinal," whether or not a battle is currently cached —
  no special-casing needed). `applyDuePendingChangesV3` is the function a
  caller invokes from `runSettlementWalkV3`'s `beforeRoll` hook; an
  integration test wires both modules together to prove a battle already
  cached before an edit keeps its old build and the very next *rolled*
  battle at the boundary gets the new one — never retroactive, never early.
  Recomputation never accumulates on an old effective-stat value because
  `computeBattleStartStatsV3` (builds3.ts) is always called fresh from the
  hero's build fields, never from a cached stat snapshot.
- `competition3.ts` implements the season (G8) and tournament (G9) pure
  surface: season epoch/window arithmetic, the four `fixture_m3_0{1..4}`
  companies (built via `autoFillLoadoutV3` at level 5, matching
  m3-systems.md section 8's exact compositions), seat-filling, the
  double-round-robin schedule builder (12 matches, pair-lexicographic
  ordering, A/B swap between legs, pluggable deterministic seed function),
  standings ranking, tournament bracket seeding (1v4/2v3 by ascending
  entryId), draw/timeout advancement tiebreak (HP -> survivors -> seed),
  and the recovery-only bye/vacancy matrix (one vacant seat -> bye; two ->
  no winner; championship title withheld unless the final was actually
  played). Server-side persistence/exactly-once guards remain M3-08.
- `dungeon3.ts` adds the M3-rules-version dungeon floor-batch runner
  (`simulateDungeonRunV3`), the piece `combat3.ts` alone didn't provide:
  sequential floor 1..N simulation using `buildEnemyCombatantsV3`, stopping
  on the first loss or the boss floor's clear, full HP every floor, with a
  normalized per-hero HP ratio output for tournament/dungeon tiebreak
  evidence. Isolated from the legacy `dungeon.ts`/`combat2.ts` pairing, same
  per-rules-version separation `combat3.ts` already established.
- `scripts/simulate-v3-tactical.mjs` (`npm run simulate:v3-tactical`) runs
  the economy/m3.md section 6 protocol for pairs (a) no-new-class
  counterexample, (b) Warder-included, (c) Weaver-included — all vs. an
  equal (zero-)gear glass-cannon five against Cinder Archive floors 1-4 —
  and (e) the three races, identical level-5 3-hero class spread, against
  Old Road. **Does not cover pair (d)**, the 16 specialization pairs;
  that remains open (see Remaining below). Measured result (32 seeds,
  reports/engineering/M3-07.md has the full output): all three Cinder
  Archive pairs cleared 100% both sides with **zero counterexamples** at
  level 5 with no equipped gear — a genuine no-contrast finding, not hidden
  by aggregation, routed to Systems/Economy per economy/m3.md section 6
  item 5's explicit "never resolved by a reward-table edit here" rule. The
  race pair shows no win-rate contrast either (full party at level vs. Old
  Road clears every seed for all three races) but does show a measurable
  rounds-to-clear spread (race_vesper 5.78 vs race_cairn/race_serein 5.09
  avg rounds across 32 seeds), consistent with the race tradeoff affecting
  combat duration even where win-rate is saturated.
- `scripts/simulate-v3-catchup.mjs` (`npm run simulate:v3-catchup`) benchmarks
  one real `runSettlementWalkV3` call at the full 8-hour cap, using actual
  `combat3` battles (5-hero balanced party vs. Old Road), 20 repetitions.
  Measured on Intel Core i7-14700K / Node v22.14.0 / win32-x64: **p95 =
  28.61ms**, far under the 2000ms target in economy/m3.md section 5 — each
  call hits the provisional `maxBattlesPerSettlement=500` cap before
  exhausting the time window (resumable catch-up, per worked example W4),
  so this is the realistic per-call cost, not a one-shot full-window cost.

## Remaining within M3-07

- Pair (d) of the tactical protocol (16 primary-specialization pairs) is
  not run. Each needs a hand-built party slotting the exact skill the
  specialization modifies; this is real remaining scope, not a stub.
- The Cinder Archive tactical measurement used zero equipped gear on both
  sides, not the "equal-budget uncommon gear" the dungeon's intended entry
  actually specifies — a simplification, not the specified condition. A
  gear-equipped rerun could show different (or no different) contrast.
- Full codex numeric/copy metadata (m3-systems.md section 6's complete
  table) is still outstanding.
- No server/database/browser wiring exists for any of this phase's modules;
  that is M3-08 (storage/transactions/receipts) and M3-09 (browser) by
  design, per this task's own scope boundary.
